Faster type checking

A slow TypeScript run leaves you guessing whether the compiler is reading too many files or spending time on a few types. You will learn to find the expensive work and simplify the types that cause it.

What you will learn
  • Read the compiler's phase timings and follow a slow comparison to its source.
  • Use an interface to describe fields that always go together.
  • Use one shared shape when a function only needs shared fields.

Where does the compiler spend its time?

The idea Use the timing summary to choose a phase, then follow a slow comparison to the types involved.

Walk through it

Suppose notes.ts passes a loaded note to two functions in cards.ts. First tsc, the TypeScript compiler, parses both files, which means turning their text into a tree it can read. Then it binds declarations, which means recording where names are defined.

While checking, the compiler compares types to see if values fit. For each call, it must ensure the loaded note has the fields the function's NoteProps type requires. Across hundreds of files, a timing summary tells you whether checking is where most of the time goes.

When Check time dominates, record a trace, a timeline of compiler work. In the diagram, a wide structuredTypeRelatedTo block shows a slow comparison. Here the target is NoteProps, the type the compiler is checking against.

The fix

Run the same compiler command with --extendedDiagnostics to see parse, bind, and check times. If parsing dominates and the file count surprises you, use --explainFiles to see why each file was included.

# Before: check types without writing JavaScript.
tsc -p tsconfig.json --noEmit
# After: show time per phase.
tsc -p tsconfig.json --noEmit --extendedDiagnostics
# If checking dominates, record a trace.
tsc -p tsconfig.json --noEmit --generateTrace ./tsc-trace

Open trace.json in a viewer that supports Chrome traces. Select the wide block and look at its sourceId and targetId. Find those IDs in types.json and follow firstDeclaration where it is present.

In this example, the target's declaration leads to NoteProps in cards.ts. Try the change in the next section and rerun the diagnostics command to see if Check time drops.

Watch out

  • Compare runs with the same files, compiler version, settings, and state of any saved results from earlier runs.
  • Use the trace to locate the slow work. Use the diagnostics run for timing because collecting a trace takes extra time.

Evidence

A draft change to simplify types in one React project cut the compiler's reported check time by about 14 seconds.

How can you make a type cheaper to check?

The idea Use an interface for fields that go together and ask only for the fields a function reads.

Walk through it

NoteProps needs the fields from NoteMeta and Timestamps, plus a title. The intersection written with & asks for all three parts at once. To check a value against it, TypeScript can have to check the parts separately.

An interface names the fields an object must provide. With extends, it brings in the fields of other object types. In the comparison diagram, the first call still checks the fields, and the second can reuse the saved result for the same pair of types.

A union written with | accepts any of its member types. A function that reads just id may accept three kinds of notes through a union. To simplify a union, the checker may compare members in pairs to see which already fit other members.

Three members give three possible pairs. With 50 members, there are 1,225 possible pairs because each member has 49 partners and each pair would otherwise count twice.

The fix

Give NoteProps one interface so the checker can reuse a comparison. Give noteId a shared type if any object with a string ID is valid input.

// Before
type NoteProps = NoteMeta & Timestamps & { title: string };
function noteId(note: DraftNote | PublishedNote | ArchivedNote) {
  return note.id;
}

// After
interface NoteProps extends NoteMeta, Timestamps { title: string }
interface HasId { id: string }
function noteId(note: HasId) { return note.id; }

Watch out

  • Check accepted and rejected calls after the change. An interface can report a conflict where two base types define the same field differently.
  • Keep the union if callers must pass only those note kinds. Test inline object literals because a shared shape can reject fields it omits.

Evidence

TanStack Table's core saw about 80 percent fewer type instantiations, or computations from type templates, after several changes including an interface rewrite.

Try it

Pick a TypeScript project where checking feels slow and run the diagnostics command from that project. Look at the check and parse times, then follow one slow comparison if checking is where the time goes.

Remember

  • Read phase timings before changing types.
  • Follow the trace from a slow comparison to the types it checks.
  • Verify the same useful calls still work and measure check time again.

Quick check

Check time is small and the compiler parses far more files than expected. Where do you start?

Run --explainFiles to see why each file is included. The reported time points to reading and parsing the project's files, so investigate that work first.

Can the checker reuse the result on the first comparison against a new interface?

It has to compare the two types before it has a result to save. A later check of the same pair can use that result.

When is HasId too broad for noteId?

It is too broad if the function should accept only the three kinds of notes. The shared shape would also accept a user with a string ID.
