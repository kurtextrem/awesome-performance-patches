How far does one style change spread?

The idea The browser rechecks every element a change could affect, so put fast-changing values on the one element that uses them, not on a parent of everything.

Walk through it

After a change, the style step marks which elements might now look different. This is called style invalidation. A class on one cell can only affect that cell and what is inside it. A CSS variable is inherited, which means every element inside can read it. So changing it on a parent makes the browser recheck all of them.

Picture a small grid: one root, 3 rows and 6 cells, so 10 elements. A scroll handler stores the scroll offset as a variable on the root, and only the rows layer uses it. In the top tree of the diagram, each scroll step marks all 10 elements red. In the bottom tree, the value is set on one row, so at most that row and its 2 cells are rechecked.

Now scale it up. A data grid with 1,000 cells rechecks 1,000 elements on every scroll step, many times a second.

The fix

Set fast-changing values directly on the element that uses them. If a value must stay a CSS variable, register it with @property and inherits: false, so changing it never spreads to children.

// Before: a variable every cell inherits, changed on every scroll step
grid.style.setProperty('--offset-top', `${top}px`);

// After: change only the element that moves
rowsLayer.style.transform = `translateY(${top}px)`;

/* If it must be a variable: stop it passing down to children */
@property --offset-top { syntax: "<length>"; inherits: false; initial-value: 0px; }

Watch out

  • A variable on the root is fine for values that rarely change, such as a theme or a compact-mode switch.
  • Moving a value into a new object prop can break React.memo on that component, as lesson 20 explains. One grid needed a second fix for exactly this.

Evidence

In a browser benchmark on a 1,000-element tree, a non-inherited registered variable was about 850 times cheaper to change than an inherited one.

Why can adding one element restyle the whole page?

The idea Add pop-ups such as tooltips to a small container that is always in the page, so the browser only rechecks that container.

Walk through it

A page has 800 elements. On hover, a tooltip library appends a tooltip straight to <body>, then reads a position to place it. The new element is a child of the element that holds everything, so the browser treats the whole page as possibly changed.

The read then forces the style step to run right away, as lesson 17 showed. In the top tree of the diagram, all 807 elements are rechecked on every hover. In the bottom tree, the tooltip goes into an always-present container, so only 3 elements are rechecked: the container, the tooltip and its text.

The fix

Put one empty container at the end of <body> when the page loads, and render every tooltip and popover into it. Most UI libraries take a container option, and React portals take a target element.

// Before: each tooltip is added straight to <body>
document.body.appendChild(tip);

// After: one small container that is always in the page
// <div id="tooltips"></div> at the end of <body>
document.getElementById('tooltips').appendChild(tip);

Watch out

  • The root cause was a read after a write, so fixing that order (lesson 17) helps too. The container keeps the damage small when you cannot change the library.
  • This was measured on an older library version. Newer ones may behave differently, so check the Recalculate Style entry yourself.

Evidence

Moving tooltips into their own container cut style recalculation from about 67 milliseconds to under 1, because 3 elements were rechecked instead of 807.

Why do layers cost time and memory?

The idea Every layer is a separate picture the browser must manage each frame, so keep layers few and small.

Walk through it

Some elements get their own layer: a separately painted picture that the composite step can move without repainting. Elements with a transform or will-change often get one. Deciding and building layers shows up in DevTools as Layerize.

Take a grid where every cell is moved into place with its own transform. With 15 columns and 20 visible rows, that can mean 300 layers to sort out on each scroll step. In the top half of the third diagram, every cell is its own sheet. In the bottom half, one empty spacer at the start of each row pushes the cells into place, so they share one layer.

Size matters as well as count. A common way to hide screen-reader text was to push it to left: -10000px. When it sat above a layered element, the browser could stretch a layer all the way out to cover it, as the last diagram shows.

The fix

Move a whole row once instead of every cell, and hide text with a tiny clipped box instead of a huge offset. Both keep the number and size of layers down.

// Before: every cell gets its own transform
<div className="cell" style={{ transform: `translateX(${x}px)` }} />
// After: one empty spacer per row, cells flow after it
<div className="cell-offset" style={{ width: offsetLeft }} />

// Before: hidden far off screen
{ position: 'absolute', left: '-10000px' }
// After: a 1 px clipped box that stays in place
{ position: 'absolute', width: 1, height: 1, overflow: 'hidden', clip: 'rect(0, 0, 0, 0)' }

Watch out

  • Each layer also uses GPU memory, so will-change on many elements can make things worse. Add it to the few elements that really animate.
  • Use the Layers panel in DevTools to see how many layers exist and how big they are before you change anything.

Evidence

Removing per-cell transforms in one data grid saved about 100 milliseconds of rendering for every 1,000 milliseconds spent, about a tenth.

Try it

Try it (3 minutes)

In Chrome DevTools, record a Performance profile while you hover tooltips or scroll a big table. Click a purple Recalculate Style block. The summary shows "Elements affected". If that is close to the whole page for a small change, look for a root variable or an element added to <body>.

Remember

  • A change on a parent can reach every element inside it, so put fast-changing values on the element that uses them.
  • Add tooltips and popovers to a small, always-present container, not straight to <body>.
  • Layers are not free: keep them few, keep them small, and check the Layers panel.

Quick check

A drag handler updates a CSS variable on the app's root on every mouse move. Why does the page stutter?

The variable is inherited, so each change makes the browser recheck every element in the app, many times a second. Set the value on the element being dragged, for example as a transform. If it must stay a variable, register it with inherits: false.

Hovering a button shows a tooltip, and Recalculate Style says 800 elements affected. What do you try first?

Check where the tooltip is inserted. If it goes straight into <body>, the browser may recheck the whole page. Render it into a small container that is always present, then check the count again.

Why can adding will-change: transform to every row slow a page down?

Each row may get its own layer, and every layer must be built, tracked and stored in GPU memory. With hundreds of rows, managing layers costs more than it saves. Promote only the few elements that actually animate.
