React re-renders

Ticking one checkbox in a long list can make React redo every row, because a parent update re-renders its children by default. After this lesson you can make unchanged rows skip, and keep per-row setup from multiplying.

  • Why per-row listeners and store subscriptions add up, and how to do them once.

Why does one checkbox re-render the whole list?

The idea When a component's state changes, React re-renders it and every child below it, unless a child is wrapped in memo and its props did not change.

Walk through it

A re-render means React calls a component function again and compares the result with last time. Take an order list with 5 cards. The list keeps the selected ids in its state, as a Set, and passes that set to every card.

Tick the checkbox on card 2. The list's state changes, so the list renders again, and so do all 5 cards. Only card 2 looks different, but React still called all 5 functions. In the top tree of the diagram, every red box is a card that rendered for nothing but card 2.

With 1,000 rows, one click means 1,000 component calls, plus the comparison work for each.

The fix

Wrap the card in memo, which skips a render when every prop is the same as last time. Then pass each card only what it needs: a selected true or false, not the whole set. Ticking makes a new set, which would count as a changed prop for every card, but the boolean only changes for card 2.

// Before: every card gets the whole set, which is new on every tick
function OrderCard({ order, selectedIds }) { /* ... */ }
<OrderCard order={order} selectedIds={selectedIds} />

// After: memo, and a boolean that only changes for the ticked card
const OrderCard = memo(function OrderCard({ order, selected }) { /* ... */ });
<OrderCard order={order} selected={selectedIds.has(order.id)} />

Watch out

  • memo is not free, because it compares props on every render. Use it on components that render often with mostly unchanged props, such as list rows.
  • A re-render is not a page update. React only touches the page for what changed, but the function calls and comparisons still cost time.

Evidence

After a spreadsheet app removed needless re-renders and repeated work around each cell edit, it did about a quarter of the JavaScript work per edit.

Why does memo sometimes do nothing?

The idea memo checks whether each prop is the very same value as last time, so a function or object created during render makes it re-render every time.

Walk through it

memo does a shallow compare. It checks each prop with Object.is, which asks "is this the very same value or object?", not "does it look the same?". This sameness of objects is called identity.

Follow card 3 after card 2 is ticked, in the diagram. order is the same object as last time. selected was false and is still false. But onSelect is an arrow function written inside the list, so each list render makes a new function. A new function is never the same object as the old one, even with identical code, so card 3 renders anyway.

The fix

Give memo props that keep their identity between renders. useCallback returns the same function until one of its dependencies changes, and useMemo does the same for a computed object or array. A constant object can move out of the component, so it is made only once.

// Before: a new function and a new object every render, so memo never skips
<OrderCard order={order} style={{ margin: 8 }} onSelect={(id) => setSelected((s) => toggle(s, id))} />

// After: the same references every render, so unchanged cards are skipped
const cardStyle = { margin: 8 };                       // outside the component
const onSelect = useCallback((id) => setSelected((s) => toggle(s, id)), []);
<OrderCard order={order} style={cardStyle} onSelect={onSelect} />

Watch out

  • A useCallback with a missing dependency keeps an old copy of the function that reads stale state. The updater form, setSelected((s) => ...), avoids needing that state as a dependency.
  • Arrays built in render, such as items.filter(...), are new every time too. Wrap them in useMemo if a memo child receives them.

Evidence

In one spreadsheet app, a grid library rebuilt an array on every render, so memo never matched and a single cell edit caused 1,568 re-renders.

Why does per-row setup add up so fast?

The idea Setup that every row repeats, such as adding the same global listener or reading the same store many times, multiplies by the row count, so do it once.

Walk through it

A dropdown has 100 items. When each item mounts, it adds the same two listeners, for keydown and mousedown, to the document. Opening the dropdown makes 200 addEventListener calls. The browser ignores the duplicates, but it still pays for every call.

In the diagram, 4 items make 8 calls at the top. At the bottom, the first item installs the listeners and the other 3 see a flag and skip. Store reads multiply the same way. If each of 1,000 items reads shared state through 10 separate useSyncExternalStore calls, that is 10,000 hook calls per render. One library merged them into one call per item and its large lists rendered 20 to 30 percent faster.

The fix

Keep a module-level flag, so the listeners are installed by the first item and skipped by the rest. For store reads, combine each item's reads into one subscription that returns everything the item needs.

// Before: every item ran the two addEventListener calls on mount
// After: the first item installs them, the rest skip
let installed = false;                    // shared by all items
function useFocusable() {
  useEffect(() => {
    if (installed) return;                // every item after the first skips
    installed = true;
    document.addEventListener('mousedown', onGlobalMouseDown, true);
    document.addEventListener('keydown', onGlobalKeyDown, true);
  }, []);
}

Watch out

  • This only helps when many components add the very same listener. Listeners that differ per row are better replaced by one listener on the list that finds the row from the click.
  • For thousands of items, virtualisation (lesson 19) still wins, because rows that do not exist do no setup at all.

Evidence

Adding the global listeners once instead of per item made a dropdown open about 30 percent faster.

Try it

Try it (2 minutes)

Open a list page in your own React app with React DevTools installed. In the Components tab settings, turn on "Highlight updates when components render", then tick one row's checkbox. If every row flashes, look for a prop that is a new set, function or object on each render.

Remember

  • A state change re-renders that component and everything below it, unless memo sees unchanged props.
  • memo compares by identity, so a new function, object or array made in render defeats it.
  • Per-row setup multiplies by the row count: install shared listeners once and merge store reads.

Quick check

An OrderCard is wrapped in memo but still renders every time the list does. What do you check first?

Check whether any prop is created during the parent's render, such as an inline arrow function, {}, [] or a new Set. memo compares by identity, so a new object counts as changed even when its contents match. Use useCallback, useMemo, or move constants outside the component.

Why pass selected={selectedIds.has(order.id)} instead of the whole set?

Ticking a box creates a new set, so every card would see a changed prop. The boolean only changes for the card that was ticked. So memo can skip all the others.

A list of 500 items each calls the same store hook 5 times. What would you change?

Merge the 5 reads into one subscription per item that returns an object with all 5 values. That cuts 2,500 hook calls per render to 500. For lists in the thousands, also consider virtualisation.
