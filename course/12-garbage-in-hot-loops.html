Garbage in hot loops

Every object your code creates has to be cleaned up later, and a loop that creates millions of throwaway objects makes that clean-up run again and again. After this lesson you can spot per-row garbage and rewrite a busy loop so it creates almost nothing.

  • Why the number of objects a loop creates decides how often your code pauses.
  • How to rewrite common per-row patterns so they create nothing new.

Where do new objects go, and who cleans them up?

The idea

New objects land in a small young area that a quick clean-up empties often, and your code pauses each time it runs.

Walk through it

Every object, array, string or function you create is stored in the heap, the memory where JavaScript values live. Storing a new value there is called an allocation. You never free memory yourself, because the garbage collector (GC) does it: it finds values nothing uses any more and reuses their space.

V8, the engine inside Chrome and Node, splits the heap in two, because most objects die young. New objects go into a small young generation. When it is full, V8 runs a quick clean-up called a scavenge.

Picture a young generation with room for 10 objects, as in the first diagram. When it fills up, 8 of the 10 are already garbage, shown in red. The scavenge copies only the 2 green survivors into a fresh, empty half, then treats the full half as empty. So its cost depends on how many objects survive, not on how much garbage there is.

An object that survives two scavenges is moved, or promoted, to the large old generation. A slower full collection cleans that area, but much less often.

A scavenge is fast, but your JavaScript stops while it runs. The second diagram shows why the number of allocations matters. Each new object fills the young generation a little more. So a loop that allocates five times as fast reaches "full", and pauses, five times as often.

The fix

You cannot switch the collector off, so the fix is to give it less to do. First, check whether it matters: count the collections while your code runs. Node reports each one as a performance entry, and node --trace-gc prints a line per collection.

// Count garbage collections while your loop runs (Node)
const { PerformanceObserver } = require('node:perf_hooks');
let gcs = 0;
new PerformanceObserver((list) => { gcs += list.getEntries().length; })
  .observe({ entryTypes: ['gc'] });

runTheLoop();
setImmediate(() => console.log('collections:', gcs)); // entries arrive a moment later

Watch out

  • Each throwaway object is cheap. Only worry when a profile shows time in garbage collection, or scavenges run hundreds of times during one task.
  • Objects you keep, such as a big array of rows, survive and get promoted, so every full collection must walk them. Lesson 14 covers that.

Evidence

In OpenTelemetry, a tracing library, one function was rewritten to allocate less. Its memory per call fell from about 1 kB to 0.4 kB, and it ran about a quarter faster.

Which everyday code creates garbage on every row?

The idea

Object.entries, spreads, chained array methods and functions written inside a loop all build throwaway objects, and a hot loop multiplies them.

Walk through it

A hot loop is code that runs once per row, per request or per item. Anything it creates is multiplied by the number of times it runs.

Take one order row with 8 number fields, and add them up. Object.entries(row) first builds an outer array, then one small [key, value] array per field. In the third diagram, that is 9 red arrays for one row, and the loop reads each one once and drops it. A for...in loop reads the fields in place, so it creates nothing.

Now scale it up. 100,000 rows read 20 times makes 2 million row visits, and 9 arrays per visit makes 18 million throwaway arrays. The young generation fills again and again, so scavenges keep interrupting the loop.

The same pattern hides in other places. { ...row, label } copies every field into a new object. .map().filter() builds a new array at each step. An arrow function written inside the loop is a new function object on every pass. The Bluebird promise library got much of its speed by creating such helper functions once, at the top level, instead of on every call.

The fix

Pick a way to loop that builds nothing new, and create helpers once outside the loop. Object.hasOwn skips keys inherited from the prototype, which Object.entries never showed you either.

// Before: 1 outer array + 8 pair arrays for every row
for (const [key, value] of Object.entries(row)) sum += value;

// After: reads the fields in place, creates nothing new
for (const key in row) {
  if (Object.hasOwn(row, key)) sum += row[key]; // skip inherited keys
}

// Copy only the fields you need, not { ...row, label }
const out = { id: row.id, status: row.status, label };

Watch out

  • Only rewrite loops that run per row or per request and show up in a profile. A loop that runs once at start-up is fine either way.
  • An explicit field list breaks quietly when someone adds a field to the source object, which the spread version would have copied.

Evidence

In OpenTelemetry, swapping Object.entries for for...in made setting 10 attributes on a span, the timing record created for each request, about 22% faster.

Remember

  • New objects go into a small young generation; a scavenge copies the survivors and pauses your code while it runs.
  • The more a loop allocates, the more often it pauses, so in hot loops avoid Object.entries, spreads, chained array methods and per-row functions.
  • Measure first: rewrite only loops that run per row or per request and show up in a profile.

Quick check

A loop uses Object.entries over 12 settings once, when the server starts. Should you rewrite it?

No. It creates 13 small arrays once, which is far too little to measure. The rewrite only pays off when the loop runs per row or per request. Then the garbage is multiplied by thousands or millions and keeps triggering scavenges.

Why does a scavenge get slower when more objects survive, but not when there is more garbage?

A scavenge copies only the objects still in use and then treats the whole full half as empty. Garbage is never touched, so it costs nothing to drop. Survivors must each be copied, so they set the price.

A profile shows a lot of garbage collection time during a per-row loop. What do you look for first?

Look for things the loop body creates on every pass. Common ones are Object.entries, { ...row } copies, .map() or .filter() chains, and arrow functions written inside the loop. Each one is multiplied by the number of rows, so removing them cuts how often the young generation fills.
