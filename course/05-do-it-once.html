Do it once, reuse the result

A loop or a refresh can spend most of its time rebuilding the same thing. You can share setup and reuse results while keeping them current.

What you will learn
  • Move setup outside a loop when its inputs stay the same.
  • Save and clear a result that several calls can reuse.

What stays the same on every pass?

The idea

When setup uses the same inputs on every pass, do it once before the loop and share what it prepares.

Walk through it

A report shows three dates using the same locale and options. The locale tells JavaScript which language and region to use. The options say which parts of the date to show and which time zone to use.

Each call to toLocaleDateString asks JavaScript to format a date with those settings. It can repeat work to prepare the settings even though only the date changes. Separating setup from formatting lets you ask for that preparation once.

The red blocks in the diagram mark repeated setup. Follow both rows until the third date is done. For 50,000 dates with identical settings, a shared formatter keeps the 50,000 formatting calls and needs just one explicit setup.

The fix

A setup whose inputs stay constant in a loop is loop-invariant. Moving it out of the loop is called hoisting. Create an Intl.DateTimeFormat with the shared settings, then change only the date passed to format.

const options = { dateStyle: 'medium', timeZone: 'UTC' };

// Before
const before = dates.map(date => date.toLocaleDateString('en-GB', options));

// After
const formatter = new Intl.DateTimeFormat('en-GB', options);
const after = dates.map(date => formatter.format(date));

Watch out

  • Reuse a formatter only for dates that share its locale and options, including the time zone.
  • A regular expression, or regex, matches a text pattern. With the g flag, a regex remembers where test() stopped. Drop that flag when checking each row for any match.

Evidence

On one machine, the course demo formatted its dates about 70 times as fast with a shared formatter.

How do you reuse a result across calls?

The idea

Save a result under a key you can look up again, and delete the entry when the source changes.

Walk through it

A list shows a plain text preview of each file. Building a preview reads and cleans the file text, so a refresh repeats that work even if the text stayed the same. Start with two files, A and B.

A cache stores results for later use. A Map stores entries as keys and values, so file A's ID can be the key for its preview. In the first diagram, a lookup for A finds an entry, while a lookup for B must build and store its first preview.

Now edit file A. Its ID stays the same, so the old preview would still be found. The second diagram shows where to remove the old entry, which makes the next read build from the new text.

If a refresh reads 10,000 files and only one has changed, the list still needs 10,000 lookups. With the other entries still present, just the edited file needs a new preview.

The fix

Saving a function's result based on its inputs is called memoising. Removing a result that has gone stale is called invalidation. Here the key is the file ID, and each successful edit must delete that key.

// Before
const previewFor = file => buildPreview(file.text);

// After
const previews = new Map();
function previewFor(file) {
  if (!previews.has(file.id)) previews.set(file.id, buildPreview(file.text));
  return previews.get(file.id);
}
const afterSave = file => previews.delete(file.id);

Watch out

  • If the preview also depends on display settings, include them in the key or clear affected entries when those settings change.
  • Saved values take memory. Keep the cache scoped to the list or give a long-lived cache a size limit.

Evidence

One author reported page blocking time below about 200 milliseconds after caching a pattern and sharing its replacement function.

Try it

From the course folder, run node demos/date-format.js.

Compare the first two timings, which use the same settings. Look for same result: true to confirm the output agrees.

Remember

  • Move setup above the loop when its inputs stay the same.
  • Save repeated results under a key that covers their inputs.
  • Clear stale entries when the source changes.

Quick check

Can dates in two different time zones share this formatter?

Each time zone needs its own formatter. The formatter holds the zone as part of its settings, and the same instant can fall on a different date in another zone.

Why clear a preview if a file edit leaves its ID unchanged?

The ID can still find the cached preview, which contains the old text. Removing that entry means the next read has to build from the edited file.
