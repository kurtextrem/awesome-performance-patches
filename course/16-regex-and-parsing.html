Regex and parsing

A regular expression, or regex, describes a text pattern, and some patterns retry the same text many ways before giving up. You’ll learn to spot retries, write more precise patterns, and read a simple format one character at a time.

What you will learn
  • You’ll trace why repeats inside repeats can make a failed match expensive.
  • You’ll see when checking ahead makes a pattern read the same characters twice.
  • You’ll follow a small scanner that keeps its place as it reads.

Why can a failed match take so long?

The idea

When two repeats can divide the same text in many ways, a failed match can make the engine retry those divisions.

Walk through it

Suppose a label needs lowercase letters followed by a colon. In /^(?:[a-z]+)+:$/, ^ and $ mark the start and end. [a-z] matches one lowercase letter in that range, and + means one or more of the thing before it.

The inner repeat takes a run of letters. (?:...) groups it, so the outer + asks for one or more runs.

Try abc, with the colon missing. The engine can first take abc as one run and fail to find a colon. It can then shorten that run to ab and use a second run for c.

This retry still fails. Going back to try a different match is called backtracking. The diagram shows four ways to use all the letters.

There are two possible breaks between three letters, and each break can be present or absent. Each extra letter adds another break and doubles the choices. With twenty letters, there are more than half a million possible full divisions. An engine may skip some paths.

The fix

One run is enough to describe the label. With one +, the engine may still shorten the run after a failure, but it has no reason to divide it into more runs.

// Before
const nested = /^(?:[a-z]+)+:$/;

// After
const single = /^[a-z]+:$/;

Watch out

  • Include failed matches when you measure a pattern, because a valid input may match on the first path.
  • Remove a repeat only when it describes the same accepted strings. A separator between runs can make the grouping part of the format.

Evidence

In a separate Java settings parser benchmark, reading characters directly was at least four times as fast as trying several regexes per line.

When does looking ahead repeat work?

The idea

A lookahead can read text without advancing the match, so the next part of the pattern may read the same text again.

Walk through it

Now check a label and a number, like tag:7. A lookahead is a check that leaves the match position where it started. In a regex, (?=...) checks that its contents match from the current position.

Suppose (?=[a-z]+:) first checks for letters and a colon. It reads tag: and succeeds, but the next part still starts at the t. The diagram highlights the same span being read twice.

On a long label, the second pass rereads the whole label. A lookahead that checks one character can be much cheaper.

The fix

Match the letters and colon once, then read one or more digits with [0-9]+. Matching the prefix already proves it is present.

// Before
const checkTwice = /^(?=[a-z]+:)[a-z]+:[0-9]+$/;

// After
const checkOnce = /^[a-z]+:[0-9]+$/;

Watch out

  • A lookahead may enforce a rule the rest of the pattern misses. Check that both versions accept and reject the same cases before changing it.

Evidence

In a separate valibot email benchmark, a revised pattern without lookaheads did about 50 percent more matches per unit of time.

When can a scanner read the format directly?

The idea

A scanner uses the current character and position to decide what to read next.

Walk through it

Parsing turns text into parts your program can use. Suppose you want a lowercase key and any text after the first colon. In tag:7:ok, that gives you the key tag and the value 7:ok.

A scanner uses a cursor, which is a number that tracks its place. The cursor advances one step for each letter and stops at the colon. The diagram shows how that position determines both slices.

Across thousands of rows, the loop reads only the key on each row. Each colon ends that row’s scan of the key, so more colons in the value create no new choices.

The fix

Advance while the key has lowercase letters. Require at least one letter and a colon, then slice the two fields. The regex below returns the same fields, with s allowing its dot to read line breaks in the value.

// Before
const fields = line => /^([a-z]+):(.*)$/s.exec(line)?.slice(1) ?? null;

// After
function scan(line) {
  let i = 0;
  while (line[i] >= 'a' && line[i] <= 'z') i++;
  if (i === 0 || line[i] !== ':') return null;
  return [line.slice(0, i), line.slice(i + 1)];
}

Watch out

  • A scanner owns every rule in the format. Check empty fields and any special rules for quotes or escaped separators.
  • Keep the regex if it is clear and fast enough. Measure on your inputs before taking on a scanner.

Evidence

In a Less experiment, a scanner that skipped copying each piece of syntax ran about 20 times as fast as the global regex version.

Remember

  • Check how many ways repeated groups can divide the same text.
  • Check how far a lookahead reads before the main pattern starts.
  • Try a cursor when a simple format spends too much time in several pattern checks.

Quick check

Why can the nested repeat retry after reading all of abc?

The missing colon makes the match fail, but the engine still has other ways to divide the letters into runs. A single repeat removes those choices about where to divide them.

Where does the main match start after the lookahead sees tag:?

It starts at the t. The lookahead confirms that text is present and leaves the starting position unchanged.

Why does the scanner keep the second colon in tag:7:ok?

Its cursor finds the end of the key at the first colon. The value is everything after that position, so it includes the second colon.
