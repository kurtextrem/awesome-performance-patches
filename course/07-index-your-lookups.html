Index your lookups

Looking up a customer for every order can mean reading the same list over and over. You can build an index, a collection that speeds up lookups, or use a simple check for short lists.

What you will learn
  • Count the work that find() repeats and build a Map once.
  • Use a Set for repeated yes or no checks, and keep tiny lists as arrays.

Why is find() inside a loop slow?

The ideaBuild a lookup by customer ID once so every order can use it.

Walk through it

You have four orders and five customer records, in order from A to E. Each order stores a customer ID, and all four orders in this example belong to E.

For the first order, find() compares the ID with A, then B, C and D, before matching E. Starting from the beginning each time is a linear scan.

Each row of the grid starts over, so four orders take twenty comparisons. With ten thousand orders and ten thousand customers, you can reach one hundred million comparisons if every match is last.

The fix

A Map stores a value under a key, which here is the customer ID. Build it from the customer list once, then call get() with the ID on each order.

In a typical implementation, the engine computes a hash, a number based on the key, to choose a small group called a bucket. The next diagram follows E into its bucket, where the engine can check the actual keys and return E's record.

// Before
const namesByScan = orders.map(({ customerId }) =>
  customers.find((c) => c.id === customerId)?.name);

// After
const byId = new Map(customers.map((c) => [c.id, c]));
const namesByIndex = orders.map(({ customerId }) =>
  byId.get(customerId)?.name);

Watch out

  • find() returns the first match, while this Map keeps the last record for each key. Use unique IDs or keep the first entry explicitly.
  • The index takes memory. Rebuild or update it when records are added, replaced, removed, or given new IDs.

Evidence

Building an index by folder path saved pnpm about 35 seconds in the dependency graph step on its test project.

Do you only need a yes or no answer?

The ideaUse a Set for repeated checks against a long list, and start with an array for a short one.

Walk through it

Suppose you check whether incoming tags are on a list of hidden tags. This is a membership check, which asks whether a value is in a collection.

To check draft, includes() compares it with test first, then sample, then draft. For public, it checks all three and answers no.

With a thousand hidden tags, a miss can take a thousand comparisons. A Set stores unique values and can use the same kind of bucket lookup as a Map.

The diagram follows two queries down both paths. The array starts again at test, while both Set queries reuse the collection built from the three tags.

The fix

Keep includes() when there are only a few tags or when you check them once. When many lookups share a long list, build the Set before the loop and use has().

// Before
const visibleByScan = tags.filter((tag) => !hiddenTags.includes(tag));

// After
const hidden = new Set(hiddenTags);
const visibleBySet = tags.filter((tag) => !hidden.has(tag));

Watch out

  • Building a Set reads the entire list and takes extra space. A short scan can be cheaper than building or consulting a separate collection.
  • If you only iterate over values that are already unique, an array is enough. Growing a hash table can also require moving entries into new buckets.

Evidence

In Valibot’s repeated checks against three keys, both versions took about 110 milliseconds, so it switched to an array.

Try it

From the course folder, run node demos/lookup.js. Check that both versions print the same result and compare their timings, including the time to build the Map.

On one machine, repeated scans took about seventy times as long. Run it twice to see how much your own timings vary.

Remember

  • find() starts the search over for each order.
  • Build a Map once when many lookups need a value by key.
  • Use Set.has() for repeated checks on a long list and includes() on a tiny one.

Quick check

How many comparisons do four orders take if their customer is always first?

Four comparisons are enough because each find() stops at the first match. Building a Map would still visit all five customers during setup.

What would you use for a fixed list of three hidden tags?

Start with an array and includes(). Even a miss needs only three comparisons, so a separate collection may offer little benefit.
