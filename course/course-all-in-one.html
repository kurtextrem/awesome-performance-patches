Is it computing or waiting?

A slow step is either busy computing or sitting idle while it waits for a database or the network, and the two need different fixes. After this lesson you can time each step with two clocks and tell which kind of slow you have.

What you will learn
  • What wall time and CPU time are, and how comparing them tells computing apart from waiting.
  • How to time each step of a job, so you fix the slow step instead of the one you guessed.

How can two clocks tell computing from waiting?

The idea Measure real time and processor time for each step: close together means computing, and processor time far below real time means waiting.

Walk through it

A stopwatch such as console.time() tells you how long a step took, but not why. Two clocks answer the why. Wall time is the real time that passes, like the clock on the wall, and it is what a user waits through. CPU time counts only the moments when the processor is actually running your code.

The course demo has a fetch step that asks a pretend database for 25,000 rows. It waits 400 ms for the answer, then turns the answer into objects. While it waits, the processor has nothing to run, so the CPU clock stops. The wall clock keeps going.

In the first diagram, the long outlined bar is the wall clock and the two thin solid slivers are the CPU clock. Fetch takes about 410 ms of wall time but only 12 ms of CPU time. So for about 97 percent of the step, the processor was idle, which means it had nothing to do.

The second diagram puts all three steps of the demo on one scale. The build step matches 20,000 orders to 5,000 customers. It takes about 327 ms of wall time and 322 ms of CPU time, so the processor was busy almost the whole time. The write step, which joins the rows into text, takes about 2 ms.

This matters more as a job grows. If a page makes 20 waits of 400 ms one after another, that is 8 seconds of wall time with almost no CPU time. A faster processor would not save one of those seconds, because the processor was never what held it up.

When CPU time is close to wall time, the code is CPU-bound: it is slow because it computes. A profile shows where (lesson 02). When CPU time is far below wall time, the code is I/O-bound. It waits for input and output, such as the network, the disk or a database. Then you cut or overlap the waits instead (lesson 10).

The fix

Wrap each step in a small helper that reads both clocks. performance.now() gives wall time in milliseconds. process.cpuUsage() gives CPU time in microseconds, so the helper divides it by 1,000.

// Before: one clock, so you only learn "slow"
console.time('fetch'); const data = await fetchRows(); console.timeEnd('fetch');

// After: two clocks around any step
async function stage(name, fn) {
  const wall0 = performance.now(), cpu0 = process.cpuUsage();
  const result = await fn();
  const cpu = process.cpuUsage(cpu0); // microseconds since cpu0
  console.log(name, 'wall', performance.now() - wall0, 'cpu', (cpu.user + cpu.system) / 1000);
  return result;
}

Watch out

  • process.cpuUsage() counts the whole Node process, including other requests running at the same moment. Measure in a script or on a quiet machine.
  • CPU time can come out slightly above wall time, because Node also runs helper threads, for example for garbage collection. Read "close" as close.

Evidence

Turning on npm's progress bar once made an install take about 49 seconds instead of 32. About 13 of the extra 17 seconds were CPU time, so the progress bar was computing, not waiting.

Why time each step instead of the whole job?

The idea Time every step separately before you change anything, because one total cannot tell you which step to fix, and guesses are often wrong.

Walk through it

The whole demo job takes about 739 ms. That is the sum of its three steps: 410 for fetch, 327 for build and 2 for write. With only the total, you have to guess where the time goes.

A common guess is the write step, because building one big string of text sounds expensive. In the diagram, that guess is the thin sliver at the right end. Even if writing became free, the job would get 2 ms faster, which is less than 1 percent.

Timed per step, the picture changes. Two steps hold almost all the time, and they are different kinds of slow. Fetch is waiting, so fewer or overlapping requests would help. Build is computing, so a profile will show which line keeps the processor busy.

Real jobs have 10 or 20 steps, so a guess is even more likely to miss. The slow part is often a small helper nobody suspected, called thousands of times. Timing every step costs a few lines and removes the guessing.

The fix

Replace the single total with one stage() call per step, using the helper from section 1. Then fix the biggest step first, and pick the tool by the two clocks.

// Before: one total for the whole job
console.time('report');
await makeReport();
console.timeEnd('report'); // "report: 739ms", but which part?

// After: one line per step, both clocks each
const data = await stage('fetch', fetchRows);
const rows = await stage('build', () => buildRows(data));
await stage('write', () => writeCsv(rows));

Watch out

  • Start with the biggest step. Halving a 2 ms step saves 1 ms; halving a 327 ms step saves about 160 ms.
  • Run the job a few times before you trust a number, because the first run is often slower. Lesson 03 explains why.

Evidence

When the slow npm install was profiled, about 23 percent of the program's time sat in one progress-tracking method. Few people would have guessed it.

Quick check

A report takes 90 seconds of wall time but only 8 seconds of CPU time. Where do you look first?

At the waiting, not the code. The processor was busy for less than a tenth of the time, so a CPU profile would show mostly idle. Count the database queries and network requests, and see which ones can be combined or run at the same time.

A step takes 300 ms of wall time and 295 ms of CPU time. Will a faster database help it?

No. The two clocks are almost equal, so the step is computing for nearly all of its time. A database that answers sooner cannot shorten work the processor is doing; a profile of this step will show where that work is.

Your timer says the whole job takes 2 seconds. Do you know what to fix?

Not yet. A total cannot tell you which step holds the time, or whether that step is computing or waiting. Time each step with both clocks first, then start with the biggest one.

How does a profiler see where the time goes?

The idea A sampling profiler pauses your program about once per millisecond and notes which functions are running. The function caught in the most snapshots is where the time goes.

Walk through it

The call stack is the chain of function calls active at one moment. In the lesson 01 demo, report calls buildRows, and buildRows calls the find() callback (called "find cb" in the diagrams). While the callback runs, all three are on the stack, and the callback is the one doing the work.

A sampling profiler, such as the one Node starts with node --cpu-prof, does not time each call. About once per millisecond it pauses the program and copies the stack. Each copy is called a sample.

Pretend the profiler took only 10 samples of the demo. In the diagram, samples 1 to 4 land while fetch waits, so no JavaScript is running and the profiler writes down (idle). Samples 5 to 10 land in build. Five of them caught the callback running, and sample 7 caught buildRows itself, between two calls.

The real run lasts about 740 ms, so it collects about 740 samples, not 10. The proportions stay roughly the same. A function that runs for 300 ms shows up in about 300 samples, which is why counting samples works as a clock.

The fix

Stop adding timers around hunches. Let the profiler watch every function at once, with no code changes, and open the file it writes in a viewer.

// Before: timers only where you already suspect a problem
console.time('find'); /* ... */ console.timeEnd('find');

// After: sample every function, then open the file
// node --cpu-prof --cpu-prof-dir=/tmp/prof demos/stages.js
// Open the .cpuprofile in Chrome DevTools (Performance panel) or speedscope

Watch out

  • A CPU profile only sees computing. Waiting shows up as (idle), so an I/O-bound step looks empty rather than slow.
  • Samples are an estimate. Tiny functions called very often can be missed, and a short run gives few samples, so repeat the action or use bigger input.

Evidence

A profile of one large pnpm install found two functions redoing the same work. Fixing them took the install from about 64 seconds to about 14.

What is the difference between total time and self time?

The idea Total time counts every sample a function appears in. Self time counts only the samples that caught it running its own lines, so self time points at the work.

Walk through it

A flame graph merges the samples. Matching stack entries are joined into one bar, and each bar's width is the number of samples it appeared in. In DevTools and speedscope, callers sit above the functions they call. Merged views, such as speedscope's Left Heavy, sort the bars, so left to right is not time order. The DevTools Performance panel shows a flame chart instead, which keeps time order.

In the diagram, report is 6 samples wide, because it was on the stack in all six build samples. buildRows is also 6 wide. The callback is 5 wide.

Total time is the full width of a bar. Self time is the part of a bar with nothing underneath it, because those are the samples where that function itself was running. So buildRows has a big total but a small self, and the callback is all self:

FunctionTotal (samples)Self (samples)
report60
buildRows61
find callback55

In a real profile with hundreds of functions, the biggest totals belong to the outer callers, such as a request handler. They are wide because everything runs under them, not because their own lines are slow. Sort by self time to find the lines that actually use the processor.

The fix

Make self time easy to read by naming hot callbacks. An arrow function passed inline has no name, so profiles show it as (anonymous). A named function expression shows up under its name.

// Before: appears in the profile as "(anonymous)"
orders.map((o) => customers.find((c) => c.id === o.customerId));

// After: appears as "matchCustomer"
orders.map((o) => customers.find(function matchCustomer(c) {
  return c.id === o.customerId;
}));

Watch out

  • High total with low self means "look further down", not "optimise this function".
  • Most viewers also show the file and line of each function, which helps when a name is missing.

Evidence

Profiles of one build pipeline showed a regex in a CSS plugin running on every rule. Skipping it in files without the special comments it looks for saved about 4.6 seconds.

Which bar do you fix?

The idea Start at the widest bar and step down while the bars stay wide. Stop at a wide bar with nothing underneath: its own code is the target.

Walk through it

Real flame graphs have hundreds of bars, so you need a route. The diagram shows an illustrative profile of a server building a report under load. Its top row splits all samples between (idle), handleRequest and the garbage collector, which frees unused memory.

Step 1: pick the widest bar that is not idle. Here that is handleRequest, at about 55 percent of all samples. Step 2: look at the bars directly under it and follow the widest one, buildReport (44 percent), then buildRows (40 percent). Each is still wide, so the time is still further down.

Step 3: matchCustomer is about 34 percent wide and has nothing underneath it. Its self time is its whole width, so its own lines do the work, and it is the target. In the demo, this is the find() callback. It scans up to 5,000 customers for each of 20,000 orders, which is up to 100 million comparisons.

The small grey bars, such as the 4 percent ones beside buildRows and matchCustomer, are cheap to ignore. Even making them free would save only a few percent.

The fix

Fix the target, then profile again. Here the fix is a Map built once, which lesson 07 explains in detail. After the change, the old target should shrink to a sliver, and a different bar becomes the widest.

// Before: each of 20,000 orders scans up to 5,000 customers
const name = customers.find((c) => c.id === o.customerId).name;

// After: build the lookup once; each order is then one direct jump
const byId = new Map(customers.map((c) => [c.id, c]));
const name = byId.get(o.customerId).name;

Watch out

  • Change one thing at a time and measure after each change, so you know which change helped.
  • Garbage collector time is real time too. A wide garbage collector bar means the code creates many short-lived objects (lesson 12).

Evidence

The TanStack Start team repeated this loop on one server-rendered page and went from about 430 to about 2,360 requests per second.

Benchmarks you can trust

A quick timing loop can report a big win that is not real, because the engine and the machine both change what you measure. After this lesson you can spot the three usual traps and set up a comparison whose answer you can believe.

  • Why you repeat and alternate runs before you believe a difference.

Why are the first rounds slower?

The idea The engine speeds code up while it runs, so run some throwaway rounds first and time only the rounds after them.

Walk through it

A benchmark is a small program that times one piece of code, often to compare two versions. Say you wrote a faster price formatter and want proof, so you call it a million times and time the loop.

V8, the JavaScript engine in Node and Chrome, first runs a function in an interpreter. The interpreter starts quickly but runs slowly, because it works through your code one small step at a time. When a function has run many times, the JIT compiler turns it into fast machine code. JIT means just in time: it compiles while the program runs.

In the diagram, each bar is one round of calls. The first rounds are tall because they run in the interpreter. Then the compiled code takes over, and the bars drop and stay low. If you average all twelve rounds, the slow early ones pull your number up.

This hurts short benchmarks most. If each version runs for only a few rounds, one may still be in the interpreter while the other is already compiled. Then you are comparing warm-up, not code.

The fix

Run throwaway rounds before you start the clock, so the timed rounds all run compiled code. This loop still has a second problem, which the next section fixes.

// Before: the clock includes the slow first rounds
console.time('format');
for (let i = 0; i < 1e6; i++) formatPrice(i);
console.timeEnd('format');

// After: warm up first, then time
for (let i = 0; i < 1e5; i++) formatPrice(i); // warm-up, not timed
console.time('format');
for (let i = 0; i < 1e6; i++) formatPrice(i);
console.timeEnd('format');

Watch out

  • Decide which speed matters. A server runs warm for hours, while a command-line tool that runs once spends much of its life cold.
  • The compiler tunes code to the inputs it has seen, so warm up with realistic inputs, not one repeated value.

Evidence

The TanStack Start team gave their server a 2-second warm-up before each 30-second load test, so their numbers reflect warmed-up code.

Can the engine skip the work you are timing?

The idea If nothing uses a result, the compiler may delete the work that produced it, so make every benchmark use its result.

Walk through it

Look again at the loop above. It calls formatPrice(i) a million times and throws every result away. The compiler may notice that the result is never used. If it can also prove the call changes nothing else, it can remove the call. This is called dead-code elimination.

In the diagram, the top row shows what can happen. You wrote a loop with a call in it, but the compiled loop is empty. The timer then measures a million rounds of nothing, and your new formatter looks impossibly fast.

The bottom row keeps the work. Each result is added to a running total, often called a sink, and the total is printed at the end. Now the compiler must run every call, because the printed number depends on all of them.

A useful warning sign: if a benchmark takes about as long as an empty loop, the work was probably removed. Formatting a number into text should cost clearly more than doing nothing.

The fix

Make the output depend on every result. Add something small from each result to a sink, and print the sink once at the end.

// Before: the result is unused, so the call may be removed
for (let i = 0; i < 1e6; i++) formatPrice(i);

// After: every result feeds the sink, and the sink is printed
let sink = 0;
for (let i = 0; i < 1e6; i++) sink += formatPrice(i).length;
console.log(sink); // the output now depends on every call

Watch out

  • Using the result adds a tiny cost of its own, such as one addition. Do the same thing in both versions, so it cancels out.
  • bench-node uses results for you, and by default stops V8 from optimising the test function. Its README calls its results "accurate but not realistic", so confirm any win in the real app.

Evidence

bench-node's documentation shows a test flagged at about 4 nanoseconds per run, because an empty function took about 0.8 nanoseconds. Only about 5 times slower than doing nothing is suspicious.

Why repeat and alternate runs?

The idea Timings wobble from run to run. So repeat each version many times, take turns between them, and let a statistical test decide whether a gap is real.

Walk through it

Noise is the run-to-run wobble that has nothing to do with your code. Other programs, the processor changing speed and garbage collection all shift timings. Run the same code twice and you get two different numbers.

Now compare old code A with new code B, which are really the same speed. You run A four times, then B four times. In the first diagram, a busy spell from another program lands during the B runs only, so B looks slower for no real reason. Alternating A, B, A, B spreads the same spell over both, so the comparison stays fair.

Repeating also gives you a spread of numbers instead of one. In the second diagram, each dot is one run. When the two spreads overlap, you cannot tell A from B. When they sit apart, the difference is real. A t-test is a statistical test that does this check with numbers instead of your eyes.

The fix

Use a small benchmark library instead of a hand-written loop. bench-node repeats each test, compares it with a baseline and, with ttest on, runs a t-test on the gap. The --allow-natives-syntax flag lets it use V8's internal commands, which it needs to control optimisation.

// Before: one run each, all A then all B, read by eye
// After: repeated runs, a baseline, and a test of the gap
const { Suite } = require('bench-node');
const suite = new Suite({ ttest: true }); // is the gap real, or noise?
suite.add('old', { baseline: true }, () => oldFormatPrice(1234));
suite.add('new', () => newFormatPrice(1234));
suite.run(); // run with: node --allow-natives-syntax bench.js

For whole browser pages, Tachometer alternates the two versions in fresh browser runs until it is confident about the gap. For command-line tools, its author points to Hyperfine.

Watch out

  • Do not stop measuring the moment you see the answer you hoped for. Decide the number of runs before you start.

What can you rule out before measuring?

The idea

A quick check can skip an expensive step once you know its result cannot affect the answer.

Walk through it

A chart has six labels, each with a center position along the bottom axis. The chart draws a label only if its center is inside the view and its text fits. To find out whether the text fits, the code asks the browser for its width.

Suppose the visible range is 20 through 40. The six centers are 0, 10, 20, 30, 40 and 50. In the first diagram, the top row measures all six labels and then checks their positions. The bottom row checks each center first, which leaves only three measurements.

When a page has pending size or position changes, a width read can make the browser calculate those sizes and positions immediately. That is called forced layout. The second diagram shows where that work can enter the measurement, and Lesson 17 explains when it happens.

With 10,000 candidate labels and 500 centers in view, the same rule leaves 500 width reads on one pass. Real charts may revisit a label, so a count of measurements and a count of points describe different things.

The fix

Return as soon as the center fails the range check. This is an early exit, and the check that causes it is called a guard clause. Candidates that pass still need the original width and fit checks.

const inView = center => center >= 20 && center <= 40;
// Before
const visible = label => {
  const width = measureText(label.text);
  return inView(label.center) && fits(label, width);
};
// After
const visible = label => {
  if (!inView(label.center)) return false;
  return fits(label, measureText(label.text));
};

Watch out

  • Keep the inclusive bounds if labels centered on either edge can appear.
  • If the product allows a label centered outside the view to overlap it, a center check can hide valid labels.

// Before

What stays the same on every pass?

const options = { dateStyle: 'medium', timeZone: 'UTC' };

How do you reuse a result across calls?

The idea

Save a result under a key you can look up again, and delete the entry when the source changes.

Walk through it

A list shows a plain text preview of each file. Building a preview reads and cleans the file text, so a refresh repeats that work even if the text stayed the same. Start with two files, A and B.

A cache stores results for later use. A Map stores entries as keys and values, so file A's ID can be the key for its preview. In the first diagram, a lookup for A finds an entry, while a lookup for B must build and store its first preview.

Now edit file A. Its ID stays the same, so the old preview would still be found. The second diagram shows where to remove the old entry, which makes the next read build from the new text.

If a refresh reads 10,000 files and only one has changed, the list still needs 10,000 lookups. With the other entries still present, just the edited file needs a new preview.

The fix

Saving a function's result based on its inputs is called memoising. Removing a result that has gone stale is called invalidation. Here the key is the file ID, and each successful edit must delete that key.

// Before
const previewFor = file => buildPreview(file.text);

// After
const previews = new Map();
function previewFor(file) {
  if (!previews.has(file.id)) previews.set(file.id, buildPreview(file.text));
  return previews.get(file.id);
}
const afterSave = file => previews.delete(file.id);

Watch out

  • If the preview also depends on display settings, include them in the key or clear affected entries when those settings change.
  • Saved values take memory. Keep the cache scoped to the list or give a long-lived cache a size limit.

Evidence

One author reported page blocking time below about 200 milliseconds after caching a pattern and sharing its replacement function.

When is a short call doing extra work?

The idea

Walk through it

A file exporter generates names from a fixed folder and file numbers. path.join puts the parts together and normalises the result, which means it cleans up things like repeated separators and parent steps. A parent step written as .. goes back up one folder.

On a system that uses slashes, both cases in the diagram begin in the files folder. Only the second case has a parent step to remove. For 10,000 generated paths with simple parts, that is 10,000 cleanups with nothing to change.

new URL also reads and normalises text to produce a structured value. TanStack Router could skip that work when it already had a suitable link and no rule for rewriting it. The query is the part after the question mark. In the diagram below, watch what gets rebuilt as three query values are added.

React Router built a separate URLSearchParams collection and assigned the finished query text once. The separate collection holds the name and value pairs without updating a URL on each append. With thousands of values, this avoids rebuilding the growing query again and again.

The fix

For generated paths, join clean parts with the system's separator, path.sep. For a URL, keep the built-in when you need its parsing or normalisation rules.

import path from 'node:path';
// These two parts always contain plain names.
const parts = ['files', 'a.txt'];

// Before
const cleaned = path.join(...parts);

// After
const joined = parts.join(path.sep);
// Before: each append rewrites url.search
for (const v of values) url.searchParams.append('id', v);

// After: build the query once, assign it once
const query = new URLSearchParams();
for (const v of values) query.append('id', v);
url.search = query.toString();

Watch out

  • Leave path cleanup in place when parts may be empty or contain separators or parent steps. Validate untrusted paths separately.
  • Reusing URL text needs the same care. A URL starting with two slashes can name another host.

What does a new Error capture?

Suppose three rows fail inside checkRow, called from readRows, which was called by importFile. Each column in the diagram is a failed row. Each captured list repeats the same chain, and the caller uses only the message.

If 10,000 rows fail and the engine captures those three calls each time, it records 30,000 frames. A result object keeps the message and the failure flag.

The fix

Return a result so the caller can handle a missing field without constructing an Error. Both versions here return a value the caller checks.

// Before
const checkRow = row =>
  row.name ? { ok: true } : { ok: false, error: new Error('Missing name') };

// After
const checkRow = row =>
  row.name ? { ok: true } : { ok: false, message: 'Missing name' };

Watch out

  • Keep errors when you need the stack to diagnose a failure. Update callers if they used to expect an Error object.
  • Error.stackTraceLimit caps the number of frames in engines that support it. Changing it affects other code too, and shorter traces can hide useful callers.

What if small calls share one setup?

The idea

When several pieces can go out together, send them through a single call and pay its setup cost once.

Walk through it

Suppose an export already has three pieces of text, A, é and !. Encoding turns text into bytes so it can be stored or sent. TextEncoder.encode produces bytes in a standard encoding called UTF-8.

The top row of the diagram sets up an encoding call for each piece. The bottom row joins the pieces and then sets up one call. Both rows convert the same text and send the same bytes in order.

With 10,000 ready pieces, groups of 100 reduce the number of calls to 100. The amount of text to convert stays the same. Making each call handle several pieces is called batching.

The fix

Collect a group of fragments that the receiver can consume as one piece. Join them without adding a separator, then encode the group.

const encoder = new TextEncoder();
const parts = ['A', 'é', '!'];

// Before
const separate = parts.map(part => encoder.encode(part));

// After
const batch = encoder.encode(parts.join(''));

Watch out

  • A larger batch may hold more memory and delay the first bytes. Batch pieces you can send promptly.
  • A surrogate pair is the two string units JavaScript uses for some characters. If fragments split the pair, separate calls encode two replacement characters, while the joined call encodes the original character.

Evidence

Astro's benchmark of a page with many small links saw average response time drop by roughly half after batching encoding.

Why is find() inside a loop slow?

The ideaBuild a lookup by customer ID once so every order can use it.

Walk through it

You have four orders and five customer records, in order from A to E. Each order stores a customer ID, and all four orders in this example belong to E.

For the first order, find() compares the ID with A, then B, C and D, before matching E. Starting from the beginning each time is a linear scan.

Each row of the grid starts over, so four orders take twenty comparisons. With ten thousand orders and ten thousand customers, you can reach one hundred million comparisons if every match is last.

The fix

A Map stores a value under a key, which here is the customer ID. Build it from the customer list once, then call get() with the ID on each order.

In a typical implementation, the engine computes a hash, a number based on the key, to choose a small group called a bucket. The next diagram follows E into its bucket, where the engine can check the actual keys and return E's record.

// Before
const namesByScan = orders.map(({ customerId }) =>
  customers.find((c) => c.id === customerId)?.name);

// After
const byId = new Map(customers.map((c) => [c.id, c]));
const namesByIndex = orders.map(({ customerId }) =>
  byId.get(customerId)?.name);

Watch out

  • find() returns the first match, while this Map keeps the last record for each key. Use unique IDs or keep the first entry explicitly.
  • The index takes memory. Rebuild or update it when records are added, replaced, removed, or given new IDs.

Do you only need a yes or no answer?

Why does copying an array in a loop get slow?

The ideaAppend rows to one array you own so most additions write just one slot.

Walk through it

Six rows arrive one by one. Each time you write [...previous, row], the three dots, called spread, put all previous entries into a new array.

For object rows, spread copies the references, which are links to the same objects. The whole row stays where it was, but each link still takes a slot to write.

Adding the first row copies nothing. Adding the second copies one reference, and adding the sixth copies five. Add the red slots in the diagram to get fifteen copies.

With 50,000 rows, the first addition copies zero entries and the last copies 49,999. The average is about 25,000 copies per addition. Multiply by 50,000 additions to get roughly 1.25 billion copies.

The fix

Start with one array and call push() for each row. JavaScript engines can reserve spare room, called capacity, so later pushes can write into an open slot.

When that space fills, the engine may move the entries into a larger block. The diagram shows two possible growth steps. The fifth push copies entries and the sixth uses a spare slot. The exact sizes vary by engine.

// Before
const copied = rows.reduce((previous, row) => [...previous, row], []);

// After
const collected = [];
for (const row of rows) collected.push(row);

Watch out

  • Append to an array your function created. For a shared array such as React state, make one copy first if the original must stay intact.
  • concat() can read all earlier entries again, so replacing spread with a different copying method keeps the same growth problem.

How can you take the oldest job without moving the rest?

The ideaAdvance the position of the next unread job so waiting jobs stay in their slots.

Walk through it

A queue gives you jobs in the order they arrived. Imagine jobs A, B, C and D waiting, with A at the front.

Calling shift() returns A and lowers the position of every waiting job by one. The top of the diagram shows all three position changes.

With a head index, the number of the next unread slot, you read A and advance that number from zero to one. B is still in slot one.

Engines can optimise small arrays. With a hundred thousand waiting jobs, repeatedly removing the first slot can be much slower than advancing a number.

The fix

For a batch you read once, loop from the first slot to the last. This reads the same jobs in order and leaves the original array intact.

// Before
while (jobs.length) processJob(jobs.shift());

// After
for (let head = 0; head < jobs.length; head++) {
  processJob(jobs[head]);
}

For a queue that keeps receiving jobs, append with push(), keep head between reads, and clear the slot as soon as you take a job. Once half the slots are used, keep just the unread part. This occasional cleanup is called compaction.

if (head * 2 >= jobs.length) {
  jobs = jobs.slice(head);
  head = 0;
}

Watch out

  • Set a consumed slot to undefined so the queue stops holding that job. Check head === jobs.length to tell when the queue is empty.
  • Use shift() when the queue stays short and simple removal meets your needs.

Evidence

How can one number store several answers?

Walk through it

A note can be archived, starred, pinned, or unread. An object can store four separate booleans, which are values that are either true or false.

A bit is one digit in base two, so it can be zero or one. A bit flag uses that digit to store one true or false answer.

Read the first diagram from right to left for the bit values. Unread is worth one and starred is worth four. Both are on, so this note's four flags fit in the number five.

The fix

Name each flag and use |, called bitwise OR, to combine them. It keeps a bit on if either input has that bit on.

The number that selects a bit is called a mask. To test STARRED, use &, called bitwise AND, which keeps a bit only if both inputs have it on. The second diagram shows why the result stays nonzero.

// Before
const note = { archived: false, starred: true, pinned: false, unread: true };
const wasStarred = note.starred;

// After
const UNREAD = 1, PINNED = 2, STARRED = 4, ARCHIVED = 8;
const flags = STARRED | UNREAD;
const isStarred = (flags & STARRED) !== 0;

Watch out

  • Keep the flag names beside the code that packs and reads them. Keep plain booleans where they make the rest of the code easier to read.
  • Bitwise operators on JavaScript Number values use 32 bits. Wider sets need another representation, such as BigInt for larger whole numbers or several words in a typed array. Rollup used BigInt flags for sets of dependencies, and Parcel moved its large flag sets to typed arrays.

Why keep each numeric field in its own array?

The ideaGroup values by field so a loop reading one field can step through neighbouring numbers.

Walk through it

Three product rows each hold a price and a stock count. If you add the prices, a loop finds each row object and reads its price.

A typed array stores values of one numeric type side by side. Make one for prices and one for stock counts. The first slot of each array belongs to the first product.

In the diagram, green marks prices two, five and eight. With columns, the loop reads those prices in order from a single block of numbers.

At a hundred thousand products, the loop still reads a hundred thousand prices. The price column keeps consecutive reads close together, which can help when the processor fetches memory in blocks.

The fix

Use one typed array per field, a layout called struct of arrays. A Float64Array can hold prices with fractions. A Uint32Array holds nonnegative whole numbers in a fixed range, which works for these stock counts.

Size both arrays from the input list and fill them using the same row positions. Then a loop that adds prices can read price alone.

// Before
const oldTotal = rows.reduce((sum, row) => sum + row.price, 0);

// After
const price = Float64Array.from(rows, (row) => row.price);
const stock = Uint32Array.from(rows, (row) => row.stock);
const newTotal = price.reduce((sum, value) => sum + value, 0);

Watch out

  • Choose a type that fits the data. For example, Uint32Array converts fractions and wraps numbers outside its range.
  • Keep row positions aligned across columns when you reorder them. Conversion takes work up front, so measure it too if you only scan once.

Why do three 20 ms lookups take 60 ms?

The ideaIf a lookup does not need another lookup's result, start it straight away, so the waits overlap instead of adding up.

Walk through it

A page needs three things: the user, the user's cart and the user's permissions. Each one is a lookup in a database or another service, and each takes 20 milliseconds (ms). Nearly all of it is waiting, not computing.

A Promise is a value that stands for a result that will arrive later. Calling getUser() starts the lookup and hands you a Promise at once. Then await pauses your function until that Promise has its result.

In the top half of the diagram, each lookup starts only after the one above it has finished. So the waits add up: three times 20 ms is 60 ms. Yet only the permissions lookup needs something from another lookup, which is the user's role.

The cart needs only the cart id, and the request already has it. So the user and the cart can both start at time zero, which we call the first wave. Permissions start when the user arrives, in the second wave, so the page is ready at 40 ms.

Now scale it up. The course demo needs nine 20 ms lookups, such as session, user, role and teams, so one after another they take 180 ms. Grouped by what they need, they form two waves. In the second diagram, each wave lasts as long as its longest chain: 40 ms, then 60 ms. So the total drops to 100 ms.

The fix

Call every independent function first, then wait for them together. Promise.all takes a list of Promises, waits until all of them have results, and returns the results in the same order as the list.

// Before: each lookup waits for the one above it
const user = await getUser(userId);
const cart = await getCart(cartId);
const perms = await getPermissions(user.roleId);

// After: wave 1 starts both lookups before waiting
const [user, cart] = await Promise.all([getUser(userId), getCart(cartId)]);
// Wave 2 needs the role from wave 1
const perms = await getPermissions(user.roleId);

Watch out

  • Promise.all fails as soon as one lookup fails, but the other lookups keep running. Use Promise.allSettled when you need every outcome, for example to clean up.
  • A wave waits for its slowest lookup. When chains differ a lot, wrap each chain in its own async function and run the chains together, as the demo does.

Why is one request for 100 items faster than 100 requests?

The ideaAsk once with all the keys instead of once per item, so you pay for one round trip, not one per key.

Walk through it

A page lists 10 orders and shows each customer's name. A common first version loads the orders with one query. Then, for each order, it loads that order's customer with its own query, which makes 11 queries.

Each query is a round trip: the request travels to the database, the database works, and the answer travels back while your code waits. Say one round trip takes 5 ms. Eleven in a row cost 55 ms, as the top row of the diagram shows.

This shape is called N+1: one query for the list plus one per row. The bottom row sends all 10 customer ids in one query, so it needs two round trips, about 10 ms. With 1,000 orders, N+1 makes 1,001 round trips, about 5 seconds.

Why not start the 10 customer queries together with Promise.all? That overlaps the waits, but the database still gets 10 requests, and it parses, plans and answers each one separately.

Requests also share a small connection pool, a fixed set of open database connections. In the diagram below the pool has 4, so 10 requests need three rounds while the batch needs one.

The fix

Collect the keys, send one query for all of them, and match the answers back by key. In SQL that is WHERE id IN (...), and for an HTTP service it is a batch endpoint.

// Before: one query per order (N+1)
for (const order of orders) {
  const [customer] = await db.query('SELECT * FROM customers WHERE id = ?', [order.customerId]);
  order.customer = customer;
}

// After: one query for all ids, then match the rows by key
const ids = [...new Set(orders.map((o) => o.customerId))];
const rows = await db.query('SELECT * FROM customers WHERE id IN (?)', [ids]);
const byId = new Map(rows.map((c) => [c.id, c]));
for (const order of orders) order.customer = byId.get(order.customerId);

When lookups are spread across many functions, such as GraphQL resolvers, a loader like DataLoader collects the keys for you. It gathers every key asked for in one turn of the event loop (lesson 11), then sends one batched request.

Watch out

  • A batch can return rows in any order and leaves out keys it did not find. Match results to inputs by key, as the Map in the code does.
  • Very long key lists can hit query or URL size limits, so split them into chunks of a few hundred (a rule of thumb).

What happens each time code reaches await?

The ideaEach await is one pass through the microtask queue, even when the value is already there, so keep work on ready values in plain functions.

Walk through it

JavaScript runs your code on one thread. The call stack holds the functions that are running right now. The event loop is the part that picks what runs next once the call stack is empty.

When a function reaches await, it stops and leaves the call stack, and the rest of it is parked. Once the awaited value is ready, a resume job goes into the microtask queue, which is a list of short follow-up jobs.

The event loop always empties the microtask queue before it takes anything from the task queue. That second queue holds timers and finished I/O, such as a network reply. So a resume runs soon, but never in the middle of other code.

Now add 4 ready numbers with sum += await x. Each number makes one pass: pause, queue the resume, empty the stack, resume, add. A plain loop does the 4 additions in one run, as the next diagram shows.

With 1,000,000 numbers there are 1,000,000 passes. In the course demo on one machine, the plain loop took about 12 ms. The await version took about 101 ms, roughly 8 times slower.

The fix

Await only the things that really wait, such as a network call. Keep helpers that work on ready values synchronous, which means they return their answer directly instead of a Promise.

// Before: async wraps plain arithmetic in a Promise, one queue pass per row
async function formatTotal(n) { return n.toFixed(2); }
for (const order of orders) totals.push(await formatTotal(order.total));

// After: a plain function returns the string directly
function formatTotal(n) { return n.toFixed(2); }
for (const order of orders) totals.push(formatTotal(order.total));

Libraries take this further. Vue's server renderer now returns a plain string when every part is ready, and returns a Promise only when it meets a real one.

Watch out

  • A function that returns either a value or a Promise is harder to call correctly. Do this only in code that runs thousands of times per request.
  • Awaiting a ready value does not let a timer or click in, because the microtask queue empties first. In the yield demo, chunks that only awaited still made a click wait about 280 ms.

Evidence

In Vue's server renderer, skipping Promises for ready values raised a mixed benchmark from about 0.3 million to 3.3 million operations per second.

Why are many small writes slower than one big one?

The ideaEvery write call has a fixed cost, so join ready pieces and write them together, just before you have to wait for something.

Walk through it

A server sends a large CSV file through a stream, which delivers a response in pieces as they become ready. The simple version calls res.write() once per row. Each call does the same bookkeeping: it checks the stream's state, turns the text into bytes and adds them to a queue.

In the diagram, each red block is that fixed cost and each blue block is one row's data. Six writes pay the fixed cost six times. One joined write sends the same six rows and pays it once.

With 5,000 rows, writing per row makes 5,000 calls, while flushing every 1,000 rows makes 5. One template engine in the sources produced 87 small chunks per page, and each chunk went through its own Promise and its own stream write.

The fix

Collect rows in an array and write the joined string when the array is full, before any real wait, and at the end. Also respect back-pressure: when res.write() returns false, the stream's buffer is full, so wait for its 'drain' event before writing more. The once helper comes from node:events.

// Before: one write call per row
for (const row of rows) res.write(toCsvLine(row));

// After: one write call per 1,000 rows
let buf = [];
for (const row of rows) {
  buf.push(toCsvLine(row));
  if (buf.length === 1000) {
    if (!res.write(buf.join(''))) await once(res, 'drain'); // buffer full: wait
    buf = [];
  }
}
res.end(buf.join('')); // the last rows, then close

Watch out

  • Bigger chunks mean the first bytes arrive later. Flush what you already have before any slow wait, so the reader can start.
  • The buffer holds memory until it is written, so keep it bounded. A thousand rows is a starting point, not a rule.

Evidence

In one streaming template engine, joining strings and flushing them only before a real wait raised throughput from about 940 to 1,550 requests per second.

Why does starting a process per request hurt?

The ideaStarting a process has a large fixed cost, so start a few helper processes once and send each job to a free one.

Walk through it

Some servers run a command-line tool for each request, for example to convert a file. A process is a running program with its own memory. To spawn one, the operating system creates it, loads the program and connects its input and output.

In Node, part of spawn() runs on the main thread and blocks it. In the top row of the diagram, three requests each spawn the tool. So the main thread is stuck three times and serves nothing else meanwhile.

In the bottom rows, the server starts two helper processes once, when it boots. For each request it only sends a short message, and a helper does the spawning. So the main thread stays free, and both helpers can work at the same time.

At scale this matters: one server that spawned per request spent about 30% of its time with the main thread blocked inside spawn(). If the helper can do the work itself, for example by loading a library once, it skips the spawn completely.

The fix

Start the helpers with fork() from node:child_process when the server starts. The code is a sketch: pickFreeHelper is your own small function, and each helper replies with a message that carries the same job id.

// Before: every request spawns the tool on the main thread
const child = spawn('convert-tool', [input, output]);
await once(child, 'close');

// After: fork two helpers once, when the server starts
const helpers = [fork('helper.js'), fork('helper.js')];
// Per request: hand the job to a free helper, which spawns the tool
pickFreeHelper(helpers).send({ id, args: [input, output] });

Watch out

  • Each idle helper holds memory. Keep the pool small and limit how many jobs may wait for a free helper.
  • Handle helpers that crash and give each job a timeout, so every caller gets a result or an error. In the same benchmark, worker threads were slower than plain spawning, so measure before choosing.

Evidence

In one Node benchmark that ran a tiny command per request, a pool of forked helpers raised throughput from about 650 to 2,200 requests per second.

Where do new objects go, and who cleans them up?

The idea

New objects land in a small young area that a quick clean-up empties often, and your code pauses each time it runs.

Walk through it

Every object, array, string or function you create is stored in the heap, the memory where JavaScript values live. Storing a new value there is called an allocation. You never free memory yourself, because the garbage collector (GC) does it: it finds values nothing uses any more and reuses their space.

V8, the engine inside Chrome and Node, splits the heap in two, because most objects die young. New objects go into a small young generation. When it is full, V8 runs a quick clean-up called a scavenge.

Picture a young generation with room for 10 objects, as in the first diagram. When it fills up, 8 of the 10 are already garbage, shown in red. The scavenge copies only the 2 green survivors into a fresh, empty half, then treats the full half as empty. So its cost depends on how many objects survive, not on how much garbage there is.

An object that survives two scavenges is moved, or promoted, to the large old generation. A slower full collection cleans that area, but much less often.

A scavenge is fast, but your JavaScript stops while it runs. The second diagram shows why the number of allocations matters. Each new object fills the young generation a little more. So a loop that allocates five times as fast reaches "full", and pauses, five times as often.

The fix

You cannot switch the collector off, so the fix is to give it less to do. First, check whether it matters: count the collections while your code runs. Node reports each one as a performance entry, and node --trace-gc prints a line per collection.

// Count garbage collections while your loop runs (Node)
const { PerformanceObserver } = require('node:perf_hooks');
let gcs = 0;
new PerformanceObserver((list) => { gcs += list.getEntries().length; })
  .observe({ entryTypes: ['gc'] });

runTheLoop();
setImmediate(() => console.log('collections:', gcs)); // entries arrive a moment later

Watch out

  • Each throwaway object is cheap. Only worry when a profile shows time in garbage collection, or scavenges run hundreds of times during one task.
  • Objects you keep, such as a big array of rows, survive and get promoted, so every full collection must walk them. Lesson 14 covers that.

Evidence

In OpenTelemetry, a tracing library, one function was rewritten to allocate less. Its memory per call fell from about 1 kB to 0.4 kB, and it ran about a quarter faster.

Which everyday code creates garbage on every row?

The idea

Object.entries, spreads, chained array methods and functions written inside a loop all build throwaway objects, and a hot loop multiplies them.

Walk through it

A hot loop is code that runs once per row, per request or per item. Anything it creates is multiplied by the number of times it runs.

Take one order row with 8 number fields, and add them up. Object.entries(row) first builds an outer array, then one small [key, value] array per field. In the third diagram, that is 9 red arrays for one row, and the loop reads each one once and drops it. A for...in loop reads the fields in place, so it creates nothing.

Now scale it up. 100,000 rows read 20 times makes 2 million row visits, and 9 arrays per visit makes 18 million throwaway arrays. The young generation fills again and again, so scavenges keep interrupting the loop.

The same pattern hides in other places. { ...row, label } copies every field into a new object. .map().filter() builds a new array at each step. An arrow function written inside the loop is a new function object on every pass. The Bluebird promise library got much of its speed by creating such helper functions once, at the top level, instead of on every call.

The fix

Pick a way to loop that builds nothing new, and create helpers once outside the loop. Object.hasOwn skips keys inherited from the prototype, which Object.entries never showed you either.

// Before: 1 outer array + 8 pair arrays for every row
for (const [key, value] of Object.entries(row)) sum += value;

// After: reads the fields in place, creates nothing new
for (const key in row) {
  if (Object.hasOwn(row, key)) sum += row[key]; // skip inherited keys
}

// Copy only the fields you need, not { ...row, label }
const out = { id: row.id, status: row.status, label };

Watch out

  • Only rewrite loops that run per row or per request and show up in a profile. A loop that runs once at start-up is fine either way.
  • An explicit field list breaks quietly when someone adds a field to the source object, which the spread version would have copied.

Evidence

In OpenTelemetry, swapping Object.entries for for...in made setting 10 attributes on a span, the timing record created for each request, about 22% faster.

If JavaScript has a garbage collector, how can it leak?

The idea

The collector frees only what nothing can reach, so a leak is an object that something long-lived still points to.

Walk through it

A full collection starts from a few roots: module-level and global variables, the functions running right now, and active timers and event listeners. It follows every reference from those roots and marks each object it reaches. A marked object is reachable and stays; everything else is freed.

Take a server with a module-level cache Map that stores each report it builds, keyed by request id. Three requests come in. In the first diagram, the two old requests, in the dashed box at the bottom left, are freed, because no root points to them any more. The three reports stay, because a path leads to each one: module scope, then cache, then the report.

Nothing ever deletes from the cache, so every request adds a report that can never be freed. Say each report is 50 KB, a made-up round number: 10,000 requests make 500 MB. That is a memory leak, memory your program still points to but will never use again.

The second diagram shows how a leak looks from outside. Healthy memory rises and falls around a flat floor. With a leak, the floor left after each collection keeps climbing.

The fix

Give every long-lived collection a way to let go: a size limit, an expiry time, or a delete when the work is done. A Map remembers the order of inserts, so its first key is always the oldest.

// Before: grows forever, reachable from module scope
const cache = new Map();
function remember(key, value) { cache.set(key, value); }

// After: keep at most 1,000 entries; drop the oldest
function remember(key, value) {
  cache.set(key, value);
  if (cache.size > 1000) cache.delete(cache.keys().next().value);
}

Watch out

  • A leak needs something long-lived, such as a module variable, a global listener or a timer. Short-lived local variables are freed normally.
  • An event listener added on every request or render and never removed is the same leak, with the event source as the root.

Evidence

In three.js, model names kept a reference into the whole model file, so one app reached about 1 GB after about 10 view changes. Lesson 15 shows why.

How can a tiny function keep a big object alive?

The idea

Functions created in the same scope share one record of its variables, so a function you cache can keep a big neighbour alive.

Walk through it

A closure is a function plus the variables around it that it can use. In V8, when any function in a scope uses a variable, that variable goes into one shared context record for the scope. Every function created there points to that same record.

Take a React component that decodes a 10 MB preview for a download button and also calls React Query, a data-fetching library. onDownload uses preview, and queryFn only uses id. Both still point to the same record, as the Before panel of the third diagram shows.

React Query keeps queryFn in its cache so it can fetch again later. The cache holds queryFn, which holds the record, which holds the preview. As the user clicks, old records and their previews pile up, so memory climbs on every click.

The fix

Move useQuery into a small custom hook. The hook is its own function, so queryFn gets its own record that holds only id.

// Leak: queryFn shares the component's record, which holds preview
const preview = decode(payload);
const onDownload = () => save(preview);
const { data } = useQuery({ queryKey: ['user', id], queryFn: () => fetchUser(id) });

// Fix: the hook's record holds only id
function useUser(id) {
  return useQuery({ queryKey: ['user', id], queryFn: () => fetchUser(id) });
}

Watch out

  • Reading the id from queryKey inside queryFn did not help in the write-up; only a separate function did.
  • This is engine behaviour, not a React Query bug, and it only matters when something long-lived, such as a cache, holds the function.

Evidence

In the write-up's demo, heap snapshots showed the 10 MB object kept alive 8 times before the fix, and flat memory after it.

Why can a retry written with .then() leak?

The idea

A promise that waits on another keeps it alive, so a retry that chains to itself grows by one link per failure.

Walk through it

A retry helper sends some data. If the send fails, it waits 100 ms and calls itself, and it returns that new attempt from inside .then(). So the first promise can only settle when the second one does, and the second only when the third does.

In the fourth diagram, each failed try adds one box to the chain. None of them can be freed, because the first promise is still waiting for the last. If the destination is down for an hour, 10 tries per second make 36,000 links for one message. Many messages retrying at once multiply that again.

The fix

Write the retry as a loop with await. The function keeps one pending try at a time, and each finished try has nothing pointing to it, so it becomes garbage.

// Before: every failure adds a link to one growing chain
function sendWithRetry(d, dest) {
  return dest.send(d).catch(() => delayMs(100).then(() => sendWithRetry(d, dest)));
}

// After: one loop, one pending try at a time
async function sendWithRetry(d, dest) {
  for (;;) { try { await dest.send(d); return; } catch { await delayMs(100); } }
}

Watch out

  • Add a maximum number of tries. Also wait a little longer after each failure, called backoff, so a dead service cannot keep work queued forever.
  • Short outages are harmless. The chain only becomes a problem during long or endless retries.

Evidence

In one 2019 write-up, thousands of streams retried this way during an outage. The process ran out of memory and crashed; the post gives no memory figures.

  • Caches need a limit, and functions you hand to a cache should come from a small scope, such as a custom hook.

Why load fields nobody reads?

The idea

Every field you load is sent, decoded, stored and later cleaned up, so ask only for the fields your code reads.

Walk through it

A list screen shows three columns: number, status and total. Each order row in the database has about 40 columns, and the code runs SELECT *, which asks for all of them.

For each row, the database sends 40 values and the program builds 40 values in memory. An ORM is a library that turns rows into objects with methods such as save(). Many ORMs wrap each row in a model object that tracks changes. Building that rich object is called hydration.

In the first diagram, the screen reads only the 3 green cells of each row, and the 37 red cells are built for nothing. With 1,000 rows, that is 40,000 values plus 1,000 model objects to show 3,000 values. At 100,000 rows the waste runs into millions of objects.

The fix

Name the fields you need. That list is a projection: the database sends only those fields, and your code builds only those. If you only read the rows, also ask your ORM for plain objects instead of models. Most have an option for this, often called raw or lean.

// Before: 40 columns per row, often wrapped in model objects
const rows = await db.query('SELECT * FROM orders WHERE status = $1', ['open']);

// After: only the 3 columns the screen shows
const rows = await db.query(
  'SELECT id, status, total FROM orders WHERE status = $1', ['open']);

Watch out

  • Plain, partial objects are for reading. Saving a partly loaded record through an ORM can overwrite fields it never loaded.
  • When the screen gains a column, add the field to the query too, or the new column stays empty.

Evidence

A log-processing service called split('\t') on every line, which built every field though only two were used. The fix moved the parser into a native Rust add-on that copies only what it keeps. Memory on one test file fell from about 381 MB to under 2 MB, as the second diagram shows.

Why hold every row when you only need one at a time?

The idea

Peak memory is what you hold at the same moment, so stream big data a batch at a time and write each result as you go.

Walk through it

An export writes 400,000 rows to a CSV file, and each row takes about 2 KB as a JavaScript object. That is a made-up round number to keep the arithmetic easy. A first version loads every row into one array, turns each into a line, and joins the lines into one big string.

While that array exists, all 400,000 rows sit in memory at once: about 800 MB, plus the string. The objects in use at one moment are called the live set, and peak memory is the largest it ever gets. In the third diagram, the red line climbs with every row read.

A stream, or a database cursor, hands you rows a batch at a time instead. With batches of 1,000 rows, the live set stays near 2 MB however many rows there are. The green line rises and falls with each batch but never grows.

The fix

Read with your database library's stream or cursor, write each line, and let the row go. One trap remains: if the file or network is slower than the database, written lines pile up in the output's buffer instead. Back-pressure is the output's signal that its buffer is full: write() returns false, so you wait for the 'drain' event before writing more. The fourth diagram shows the pause.

const { once } = require('node:events');

// Before: every row in memory, then one huge string
const rows = await db.query('SELECT id, status, total FROM orders');
out.write(rows.map(toCsvLine).join('\n'));

// After: one batch at a time; pause while the output is full
for await (const row of db.stream('SELECT id, status, total FROM orders')) {
  if (!out.write(toCsvLine(row) + '\n')) await once(out, 'drain');
}

Here db.stream stands for whatever your library calls its stream or cursor.

Watch out

  • pipeline() from node:stream connects a source to an output, handles back-pressure for you, and cleans up both ends if a step fails.
  • A cursor keeps a database resource open. If your loop can stop early or throw, close it in a finally block when your library needs that.

Evidence

None of this course's sources measured an export like this, so treat it as a rule of thumb. With streaming, peak memory is about batch size times row size, not total rows times row size.

Try it

Try it on your own export (5 minutes)

Run it with a small heap limit: node --max-old-space-size=256 export.js. On a large enough input, a load-everything version fails with "JavaScript heap out of memory", while a streaming version finishes. Log process.memoryUsage().heapUsed every 10,000 rows to watch the line stay flat.

Remember

  • Load only what you read: a projection, plus plain objects when you only read.
  • Peak memory is what you hold at once, so stream big data a batch at a time.
  • Respect back-pressure: when write() returns false, wait for 'drain', or let pipeline() do it.

Why can a short name keep a whole file in memory?

The idea

Keeping a string slice can keep its original text in memory when the two share storage.

Walk through it

Suppose you save Amber Notebook from the first line of an upload in a cache, which holds values for later use. Your cache stores the result of slice, which takes a range between two positions in a string.

V8, the engine that runs JavaScript in Node.js and Chrome, can represent that slice by recording a start, a length, and a reference. A reference is a link to data, so the slice can read its letters from the original text.

Now scale the upload to 40 megabytes while keeping the same name. In the top row of the diagram, the cache holds the slice and the slice still points into the upload. Clearing the upload variable leaves that second link in place.

The garbage collector frees data that your running program can no longer reach. It must keep the whole source string while the cached slice depends on any part of it.

The fix

When a long-lived cache holds a slice, try rebuilding just the small field. JSON.stringify writes the name as quoted text and escapes special characters, and JSON.parse reads it back into the original string value. The lower row shows the separate storage this produced in one Node.js example.

// Before
cache.set(id, upload.slice(start, end));

// After
const name = upload.slice(start, end);
cache.set(id, JSON.parse(JSON.stringify(name)));

Watch out

  • Check a memory snapshot, which records what is held in memory, for a link from the cached field to the source. Verify the change with the engine version you deploy, because the language gives no guarantee about string storage.
  • Sharing storage saves copying when the source and slice are both used briefly.

Evidence

In one three.js memory report, object names retained the text of a roughly 40 megabyte model file.

How far does a string search need to go?

The idea

Find the first separator when you need a position, and check only the beginning when you need a prefix.

Walk through it

Take note:ready:today and keep the key before the first colon. The colon is a separator, a character that divides the fields. Calling split(':') finds both colons and builds an array of three pieces before your code keeps the first.

In the first scan diagram, indexOf(':') can stop at the first colon. On a line with thousands of later separators, it can still stop at the same place. That avoids making an array and extracting the fields your code would discard.

A prefix is the start of a string. If you only want to know whether item.user.saved starts with user., the first character gives you the answer. The second scan diagram shows where the two calls can stop.

The fix

Use the position of the first colon to take the key in one slice. For a prefix, startsWith only needs to compare the leading characters, so a long suffix adds no further search.

// Before
const oldKey = line.split(':')[0];
const wasUser = type.indexOf('user.') === 0;

// After
const colon = line.indexOf(':');
const key = colon === -1 ? line : line.slice(0, colon);
const isUser = type.startsWith('user.');

Watch out

  • indexOf returns -1 when the colon is missing, so return the whole line to match split(':')[0].
  • Use split when you want all the fields. When everything after the first colon is one value, slice after it to keep any later colons intact.

Evidence

A Fastify search could scan roughly 16 kilobytes of header text before it was replaced with a prefix comparison.

Remember

  • Follow a cached string’s references when a large source stays in memory.
  • Use indexOf to find the first separator when all you need is a boundary.
  • Use startsWith when only the beginning matters.

Why can a failed match take so long?

The idea

When two repeats can divide the same text in many ways, a failed match can make the engine retry those divisions.

Walk through it

Suppose a label needs lowercase letters followed by a colon. In /^(?:[a-z]+)+:$/, ^ and $ mark the start and end. [a-z] matches one lowercase letter in that range, and + means one or more of the thing before it.

The inner repeat takes a run of letters. (?:...) groups it, so the outer + asks for one or more runs.

Try abc, with the colon missing. The engine can first take abc as one run and fail to find a colon. It can then shorten that run to ab and use a second run for c.

This retry still fails. Going back to try a different match is called backtracking. The diagram shows four ways to use all the letters.

There are two possible breaks between three letters, and each break can be present or absent. Each extra letter adds another break and doubles the choices. With twenty letters, there are more than half a million possible full divisions. An engine may skip some paths.

The fix

One run is enough to describe the label. With one +, the engine may still shorten the run after a failure, but it has no reason to divide it into more runs.

// Before
const nested = /^(?:[a-z]+)+:$/;

// After
const single = /^[a-z]+:$/;

Watch out

  • Include failed matches when you measure a pattern, because a valid input may match on the first path.
  • Remove a repeat only when it describes the same accepted strings. A separator between runs can make the grouping part of the format.

Evidence

In a separate Java settings parser benchmark, reading characters directly was at least four times as fast as trying several regexes per line.

When does looking ahead repeat work?

The idea

A lookahead can read text without advancing the match, so the next part of the pattern may read the same text again.

Walk through it

Now check a label and a number, like tag:7. A lookahead is a check that leaves the match position where it started. In a regex, (?=...) checks that its contents match from the current position.

Suppose (?=[a-z]+:) first checks for letters and a colon. It reads tag: and succeeds, but the next part still starts at the t. The diagram highlights the same span being read twice.

On a long label, the second pass rereads the whole label. A lookahead that checks one character can be much cheaper.

The fix

Match the letters and colon once, then read one or more digits with [0-9]+. Matching the prefix already proves it is present.

// Before
const checkTwice = /^(?=[a-z]+:)[a-z]+:[0-9]+$/;

// After
const checkOnce = /^[a-z]+:[0-9]+$/;

Watch out

  • A lookahead may enforce a rule the rest of the pattern misses. Check that both versions accept and reject the same cases before changing it.

Evidence

In a separate valibot email benchmark, a revised pattern without lookaheads did about 50 percent more matches per unit of time.

When can a scanner read the format directly?

The idea

A scanner uses the current character and position to decide what to read next.

Walk through it

Parsing turns text into parts your program can use. Suppose you want a lowercase key and any text after the first colon. In tag:7:ok, that gives you the key tag and the value 7:ok.

A scanner uses a cursor, which is a number that tracks its place. The cursor advances one step for each letter and stops at the colon. The diagram shows how that position determines both slices.

Across thousands of rows, the loop reads only the key on each row. Each colon ends that row’s scan of the key, so more colons in the value create no new choices.

The fix

Advance while the key has lowercase letters. Require at least one letter and a colon, then slice the two fields. The regex below returns the same fields, with s allowing its dot to read line breaks in the value.

// Before
const fields = line => /^([a-z]+):(.*)$/s.exec(line)?.slice(1) ?? null;

// After
function scan(line) {
  let i = 0;
  while (line[i] >= 'a' && line[i] <= 'z') i++;
  if (i === 0 || line[i] !== ':') return null;
  return [line.slice(0, i), line.slice(i + 1)];
}

Watch out

  • A scanner owns every rule in the format. Check empty fields and any special rules for quotes or escaped separators.
  • Keep the regex if it is clear and fast enough. Measure on your inputs before taking on a scanner.

Evidence

In a Less experiment, a scanner that skipped copying each piece of syntax ran about 20 times as fast as the global regex version.

  • Check how many ways repeated groups can divide the same text.
  • Check how far a lookahead reads before the main pattern starts.
  • Try a cursor when a simple format spends too much time in several pattern checks.

What does the browser do to draw one frame?

The idea The browser saves up your changes and lays out the page once per frame, unless your code asks for a size in the middle.

Walk through it

A screen that refreshes 60 times a second gives the browser about 16.7 milliseconds to make each picture. One picture is called a frame.

To turn a change into pixels, the browser runs the steps in the first diagram. Style works out which CSS rules apply to each element. Layout works out the size and position of every element. Paint records how to fill in the pixels, and composite stacks the painted pieces into the final picture.

The browser is lazy on purpose. When your code changes a class or a size, the browser only marks the layout as out of date. It plans to redo it once, at the end. But if your code then reads a size, such as offsetHeight, the browser cannot answer from stale data. It must run style and layout right now, which is called a forced synchronous layout, or forced reflow.

Take a link that shows a preview card on hover. The handler removes the link's title (a write), reads the link's position (a read), then inserts the card (more writes). In the second diagram, the read lands after a write, so layout runs early. The card insert then dirties it again, so layout runs twice in this frame.

The fix

Read sizes at the start of the handler, before you change anything. The page is still up to date from the last frame, so the read is cheap. Your writes then only mark layout as stale, and the browser redoes it once.

// Before: change, then measure, so layout runs early and again later
link.removeAttribute('title');       // write
const rects = link.getClientRects(); // read: forced layout
showPreview(link, rects);            // more writes

// After: measure first, while the page is still clean
const rects = link.getClientRects(); // read: cheap
link.removeAttribute('title');
showPreview(link, rects);

Watch out

  • Reads that can force layout include offsetWidth, offsetHeight, clientWidth, scrollTop, getBoundingClientRect() and getComputedStyle().
  • A read with no pending write is cheap. Avoid reads that come straight after writes, not reads in general.

Evidence

One tooltip library changed the page and then read a position. That forced the browser to restyle 807 elements on the spot, about 67 milliseconds per hover.

Why does a loop of reads and writes get so slow?

The idea Alternating reads and writes in a loop forces one layout per item, so do all the reads first and all the writes after.

Walk through it

Say 4 product cards should be square. For each card, the code reads its width and then sets its height to match. The first read is cheap, because nothing has changed yet. Each later read comes right after a write, so the browser must lay out the page again before it can answer.

In the third diagram, each red block is one of those forced layouts. With 4 cards there are 3, and the normal layout still runs at the end. With 500 cards there are 499 forced layouts in one frame. Repeated forced layout like this is called layout thrashing.

Each layout can cover the whole page, so its cost grows with page size as well as card count. That is why the same loop can feel fine on a small test page and freeze a large one.

The fix

Split the loop in two. The reads all happen while the page is clean, so none of them forces layout. The writes only mark layout as stale, and the browser lays out once, at the normal time.

// Before: read, write, read, write... one forced layout per card
cards.forEach((card) => {
  const width = card.offsetWidth;   // read after the last write: forced
  card.style.height = `${width}px`; // write
});

// After: all reads first, then all writes, so layout runs once
const widths = cards.map((card) => card.offsetWidth);
cards.forEach((card, i) => { card.style.height = `${widths[i]}px`; });

Watch out

  • Thrashing often hides across functions: a helper that writes, then another helper that reads. Look at the order of calls, not just one loop.
  • Libraries can do it too. A tooltip or chart library that measures after inserting will force layout on every use.

Evidence

What if events fire faster than frames?

The idea Let fast events only record the latest value, and apply it once per frame inside requestAnimationFrame.

Walk through it

Events such as pointermove and scroll can fire several times within one frame. Say a user drags a slider handle, and 4 pointer events arrive before the next frame. If each event moves the handle and measures it, the page does 4 updates and 4 layouts. The screen only shows the last one.

requestAnimationFrame (often shortened to rAF) runs a callback just before the browser's next style and layout. In the last diagram, each event only stores itself as the newest value. One callback waits for the frame and reads that newest value, so 4 events become 1 update.

The fix

Keep one flag that says a callback is already waiting. Every event overwrites the latest value, and only the first event in a frame schedules the callback. This works because the callback runs once per frame, whatever the event rate.

// Before: el.addEventListener('pointermove', (e) => moveHandle(e.clientX));
let latest = null;
let waiting = false;
el.addEventListener('pointermove', (e) => {
  latest = e;                 // cheap: just remember it
  if (waiting) return;        // a callback is already scheduled
  waiting = true;
  requestAnimationFrame(() => { waiting = false; moveHandle(latest.clientX); });
});

Watch out

  • Modern browsers already line up most pointer events with frames, so measure before adding this everywhere. Window resize is still better handled with a debounce.
  • Inside the callback, keep reads before writes too. rAF limits how often you update, but it does not reorder your code.

Evidence

At 120 Hz a frame has only about 8 milliseconds, so one extra layout per event can use up the whole budget.

How far does one style change spread?

The idea The browser rechecks every element a change could affect, so put fast-changing values on the one element that uses them, not on a parent of everything.

Walk through it

After a change, the style step marks which elements might now look different. This is called style invalidation. A class on one cell can only affect that cell and what is inside it. A CSS variable is inherited, which means every element inside can read it. So changing it on a parent makes the browser recheck all of them.

Picture a small grid: one root, 3 rows and 6 cells, so 10 elements. A scroll handler stores the scroll offset as a variable on the root, and only the rows layer uses it. In the top tree of the diagram, each scroll step marks all 10 elements red. In the bottom tree, the value is set on one row, so at most that row and its 2 cells are rechecked.

Now scale it up. A data grid with 1,000 cells rechecks 1,000 elements on every scroll step, many times a second.

The fix

Set fast-changing values directly on the element that uses them. If a value must stay a CSS variable, register it with @property and inherits: false, so changing it never spreads to children.

// Before: a variable every cell inherits, changed on every scroll step
grid.style.setProperty('--offset-top', `${top}px`);

// After: change only the element that moves
rowsLayer.style.transform = `translateY(${top}px)`;

/* If it must be a variable: stop it passing down to children */
@property --offset-top { syntax: "<length>"; inherits: false; initial-value: 0px; }

Watch out

  • A variable on the root is fine for values that rarely change, such as a theme or a compact-mode switch.
  • Moving a value into a new object prop can break React.memo on that component, as lesson 20 explains. One grid needed a second fix for exactly this.

Evidence

In a browser benchmark on a 1,000-element tree, a non-inherited registered variable was about 850 times cheaper to change than an inherited one.

Why can adding one element restyle the whole page?

The idea Add pop-ups such as tooltips to a small container that is always in the page, so the browser only rechecks that container.

Walk through it

A page has 800 elements. On hover, a tooltip library appends a tooltip straight to <body>, then reads a position to place it. The new element is a child of the element that holds everything, so the browser treats the whole page as possibly changed.

The read then forces the style step to run right away, as lesson 17 showed. In the top tree of the diagram, all 807 elements are rechecked on every hover. In the bottom tree, the tooltip goes into an always-present container, so only 3 elements are rechecked: the container, the tooltip and its text.

The fix

Put one empty container at the end of <body> when the page loads, and render every tooltip and popover into it. Most UI libraries take a container option, and React portals take a target element.

// Before: each tooltip is added straight to <body>
document.body.appendChild(tip);

// After: one small container that is always in the page
// <div id="l18-tooltips"></div> at the end of <body>
document.getElementById('l18-tooltips').appendChild(tip);

Watch out

  • The root cause was a read after a write, so fixing that order (lesson 17) helps too. The container keeps the damage small when you cannot change the library.
  • This was measured on an older library version. Newer ones may behave differently, so check the Recalculate Style entry yourself.

Evidence

Moving tooltips into their own container cut style recalculation from about 67 milliseconds to under 1, because 3 elements were rechecked instead of 807.

Why do layers cost time and memory?

The idea Every layer is a separate picture the browser must manage each frame, so keep layers few and small.

Walk through it

Some elements get their own layer: a separately painted picture that the composite step can move without repainting. Elements with a transform or will-change often get one. Deciding and building layers shows up in DevTools as Layerize.

Take a grid where every cell is moved into place with its own transform. With 15 columns and 20 visible rows, that can mean 300 layers to sort out on each scroll step. In the top half of the third diagram, every cell is its own sheet. In the bottom half, one empty spacer at the start of each row pushes the cells into place, so they share one layer.

Size matters as well as count. A common way to hide screen-reader text was to push it to left: -10000px. When it sat above a layered element, the browser could stretch a layer all the way out to cover it, as the last diagram shows.

The fix

Move a whole row once instead of every cell, and hide text with a tiny clipped box instead of a huge offset. Both keep the number and size of layers down.

// Before: every cell gets its own transform
<div className="cell" style={{ transform: `translateX(${x}px)` }} />
// After: one empty spacer per row, cells flow after it
<div className="cell-offset" style={{ width: offsetLeft }} />

// Before: hidden far off screen
{ position: 'absolute', left: '-10000px' }
// After: a 1 px clipped box that stays in place
{ position: 'absolute', width: 1, height: 1, overflow: 'hidden', clip: 'rect(0, 0, 0, 0)' }

Watch out

  • Each layer also uses GPU memory, so will-change on many elements can make things worse. Add it to the few elements that really animate.
  • Use the Layers panel in DevTools to see how many layers exist and how big they are before you change anything.

Evidence

Removing per-cell transforms in one data grid saved about 100 milliseconds of rendering for every 1,000 milliseconds spent, about a tenth.

Why is a long list heavy when only 20 rows show?

The idea Every element in the page costs style, layout and memory, whether or not it is on screen, so count elements and make each row lighter.

Walk through it

The DOM is the tree of elements the browser keeps for the page. Say an order history shows 2,000 orders, and each row is about 10 elements: a few cells, a badge and a button. That is 20,000 elements, but the screen shows only about 20 rows, which is 200 elements.

Style and layout work grows with the number of elements, as lessons 17 and 18 showed. So the 19,800 elements off screen still slow every restyle, and each one holds memory. In the diagram, the red bar is what the page holds and the tiny green bar is what anyone can see.

The fix

First, make each row lighter. Remove wrapper elements nobody needs, and replace an icon image inside a button with a background on the button itself. Fewer elements per row means less work on every row, on or off screen.

<!-- Before: two elements per item, and every image loads -->
<button><img src="party.png" alt="party"></button>

<!-- After: one element; the image is a background, set when on screen -->
<button class="emoji" aria-label="party" style="--img: url(party.png)"></button>
/* CSS: .onscreen .emoji { background-image: var(--img); } */

Watch out

  • Lighthouse, the page audit built into Chrome, warns above about 800 elements and reports an error above about 1,400. Treat these as rough signals, not hard limits.
  • One listener per row multiplies the same way. One listener on the list, which catches clicks bubbling up from rows, is cheaper.

An emoji picker halved its elements from about 40,000 to 20,000 this way, and its benchmark went from about 224 milliseconds to about 144.

How does virtualisation keep a list small?

The idea Virtualisation keeps only the rows near the screen in the page and swaps them as you scroll, so the page size stays the same for 2,000 or 200,000 rows.

Walk through it

Say each row is 30 pixels tall and the list box is 600 pixels tall, so 20 rows fit. The full list would be 2,000 times 30, which is 60,000 pixels. An empty spacer of that height keeps the scrollbar the right size.

When the user scrolls to 15,000 pixels, the code divides by 30 and gets row 500. It renders rows 495 to 524: the 20 on screen plus 5 extra above and below, called the buffer. In the diagram, only the solid rows exist. Everything else is empty space.

The fix

Work out the first and last row from the scroll position, render that slice, and move it down to where it belongs. Libraries such as react-window and TanStack Virtual do this for you, including rows of different heights.

// Before: render(rows) puts all 2,000 rows in the page
const ROW = 30, VIEW = 600, BUFFER = 5;
const first = Math.max(0, Math.floor(scrollTop / ROW) - BUFFER);
const last = Math.min(rows.length, first + VIEW / ROW + 2 * BUFFER);
spacer.style.height = `${rows.length * ROW}px`;          // right scrollbar
slice.style.transform = `translateY(${first * ROW}px)`;  // move into place
render(rows.slice(first, last));                         // about 30 rows

Watch out

  • Rows that do not exist cannot be found with Ctrl+F or printed. One code viewer laid a transparent text area holding the full text over the visible lines to keep Ctrl+F working.
  • Very fast scrolling can show blank space before new rows arrive. A bigger buffer in the direction of scrolling helps.

Evidence

One code viewer measured about 0.9 milliseconds per line, so a 52,000-line file would take about 47 seconds. Virtualised, it renders only the visible lines.

Can the browser skip off-screen work for you?

The idea content-visibility: auto keeps every element in the page but lets the browser skip style, layout and paint for sections that are off screen.

Walk through it

Group the 2,000 orders into 50 day sections of 40 rows each. Give each section content-visibility: auto. The browser now lays out and paints only the sections near the screen. The others stay in the page, so Ctrl+F and screen readers still find them.

A skipped section has no measured height, so the scrollbar would jump. contain-intrinsic-size gives it a guessed height to use until it comes on screen. In the diagram, the grey sections are skipped placeholders and only the middle one is drawn in full.

The fix

Add two CSS lines to each section. The auto keyword in contain-intrinsic-size tells the browser to remember the real height once it has seen the section.

/* Before: every day section is styled, laid out and painted */
.day { }

/* After: skip the work for sections that are off screen */
.day {
  content-visibility: auto;
  contain-intrinsic-size: auto 1200px; /* 40 rows of 30 px, guessed while skipped */
}

The last diagram compares all three options on the same list. Use content-visibility when sections have predictable heights and you want find to keep working. Use virtualisation when the list is very long, such as tens of thousands of rows.

Watch out

  • content-visibility is slower than virtualisation for very large lists, because every element still exists. Older Safari versions do not support it.
  • A guessed height that is far off makes the scrollbar jump as sections come into view. Base the guess on rows times row height.

Evidence

Adding content-visibility to each emoji category made the picker's benchmark about 15 percent faster in Chrome, from about 270 milliseconds to about 227.

Why does one checkbox re-render the whole list?

The idea When a component's state changes, React re-renders it and every child below it, unless a child is wrapped in memo and its props did not change.

Walk through it

A re-render means React calls a component function again and compares the result with last time. Take an order list with 5 cards. The list keeps the selected ids in its state, as a Set, and passes that set to every card.

Tick the checkbox on card 2. The list's state changes, so the list renders again, and so do all 5 cards. Only card 2 looks different, but React still called all 5 functions. In the top tree of the diagram, every red box is a card that rendered for nothing but card 2.

With 1,000 rows, one click means 1,000 component calls, plus the comparison work for each.

The fix

Wrap the card in memo, which skips a render when every prop is the same as last time. Then pass each card only what it needs: a selected true or false, not the whole set. Ticking makes a new set, which would count as a changed prop for every card, but the boolean only changes for card 2.

// Before: every card gets the whole set, which is new on every tick
function OrderCard({ order, selectedIds }) { /* ... */ }
<OrderCard order={order} selectedIds={selectedIds} />

// After: memo, and a boolean that only changes for the ticked card
const OrderCard = memo(function OrderCard({ order, selected }) { /* ... */ });
<OrderCard order={order} selected={selectedIds.has(order.id)} />

Watch out

  • memo is not free, because it compares props on every render. Use it on components that render often with mostly unchanged props, such as list rows.
  • A re-render is not a page update. React only touches the page for what changed, but the function calls and comparisons still cost time.

Evidence

After a spreadsheet app removed needless re-renders and repeated work around each cell edit, it did about a quarter of the JavaScript work per edit.

Why does memo sometimes do nothing?

The idea memo checks whether each prop is the very same value as last time, so a function or object created during render makes it re-render every time.

Walk through it

memo does a shallow compare. It checks each prop with Object.is, which asks "is this the very same value or object?", not "does it look the same?". This sameness of objects is called identity.

Follow card 3 after card 2 is ticked, in the diagram. order is the same object as last time. selected was false and is still false. But onSelect is an arrow function written inside the list, so each list render makes a new function. A new function is never the same object as the old one, even with identical code, so card 3 renders anyway.

The fix

Give memo props that keep their identity between renders. useCallback returns the same function until one of its dependencies changes, and useMemo does the same for a computed object or array. A constant object can move out of the component, so it is made only once.

// Before: a new function and a new object every render, so memo never skips
<OrderCard order={order} style={{ margin: 8 }} onSelect={(id) => setSelected((s) => toggle(s, id))} />

// After: the same references every render, so unchanged cards are skipped
const cardStyle = { margin: 8 };                       // outside the component
const onSelect = useCallback((id) => setSelected((s) => toggle(s, id)), []);
<OrderCard order={order} style={cardStyle} onSelect={onSelect} />

Watch out

  • A useCallback with a missing dependency keeps an old copy of the function that reads stale state. The updater form, setSelected((s) => ...), avoids needing that state as a dependency.
  • Arrays built in render, such as items.filter(...), are new every time too. Wrap them in useMemo if a memo child receives them.

Evidence

In one spreadsheet app, a grid library rebuilt an array on every render, so memo never matched and a single cell edit caused 1,568 re-renders.

Why does per-row setup add up so fast?

The idea Setup that every row repeats, such as adding the same global listener or reading the same store many times, multiplies by the row count, so do it once.

Walk through it

A dropdown has 100 items. When each item mounts, it adds the same two listeners, for keydown and mousedown, to the document. Opening the dropdown makes 200 addEventListener calls. The browser ignores the duplicates, but it still pays for every call.

In the diagram, 4 items make 8 calls at the top. At the bottom, the first item installs the listeners and the other 3 see a flag and skip. Store reads multiply the same way. If each of 1,000 items reads shared state through 10 separate useSyncExternalStore calls, that is 10,000 hook calls per render. One library merged them into one call per item and its large lists rendered 20 to 30 percent faster.

The fix

Keep a module-level flag, so the listeners are installed by the first item and skipped by the rest. For store reads, combine each item's reads into one subscription that returns everything the item needs.

// Before: every item ran the two addEventListener calls on mount
// After: the first item installs them, the rest skip
let installed = false;                    // shared by all items
function useFocusable() {
  useEffect(() => {
    if (installed) return;                // every item after the first skips
    installed = true;
    document.addEventListener('mousedown', onGlobalMouseDown, true);
    document.addEventListener('keydown', onGlobalKeyDown, true);
  }, []);
}

Watch out

  • This only helps when many components add the very same listener. Listeners that differ per row are better replaced by one listener on the list that finds the row from the click.
  • For thousands of items, virtualisation (lesson 19) still wins, because rows that do not exist do no setup at all.

Evidence

Adding the global listeners once instead of per item made a dropdown open about 30 percent faster.

How much time does one frame get?

The idea At 60 refreshes per second, each new picture must be ready within 16.7 ms, or the screen shows the old picture again.

Walk through it

A screen redraws itself at a fixed rate, and each still picture it shows is called a frame. At 60 refreshes per second there are 1,000 divided by 60, about 16.7 ms, between refreshes. That gap is the frame budget. On a 120 Hz screen it shrinks to about 8 ms.

Take a drawer that slides open over 300 ms. At 60 Hz that is 18 frames, so the browser must build 18 pictures, each inside its own 16.7 ms slot. Your JavaScript, style, layout and paint (lesson 17) all share that one slot.

In the diagram, frames 1 and 3 take 10 ms and fit. Frame 2 takes 25 ms, so it is not ready at the 33.3 ms refresh. The screen shows frame 1 a second time, then frame 2 arrives late and the drawer jumps. Users feel that jump as a stutter, often called jank.

The fix

If JavaScript drives the motion, update once per frame with requestAnimationFrame, which calls your function just before the browser draws. A 10 ms timer fires once or twice per refresh, so some updates are never shown and the steps are uneven. Compute the position from elapsed time, so one late frame does not slow the whole animation.

// Before: a timer on its own clock, 3 px per tick
setInterval(() => { x += 3; box.style.transform = `translateX(${x}px)`; }, 10);

// After: once per frame, position from elapsed time
const start = performance.now();
function step(now) {
  const t = Math.min((now - start) / 300, 1); // 0 to 1 over 300 ms
  box.style.transform = `translateX(${t * 300}px)`;
  if (t < 1) requestAnimationFrame(step);
}
requestAnimationFrame(step);

Watch out

  • requestAnimationFrame only decides when your code runs. If the work inside takes 25 ms, the frame is still late.
  • A fast laptop hides missed frames. Test with CPU throttling in DevTools or on a slow phone.

Evidence

The Motion animation guide puts the budget at 16.7 ms per frame at 60 frames per second, and about 8 ms at 120.

Which properties are cheap to animate?

The idea Animate transform and opacity, because the browser can reuse pixels it already drew instead of redoing layout and paint.

Walk through it

Each frame passes through stages. Style works out which CSS rules apply. Layout works out the size and position of every box. Paint turns boxes into pixels. Composite stacks finished pieces, called layers, into the final picture.

Animate the drawer's width from 0 to 420 px, and each of the 18 frames has a new width. Text rewraps and boxes move, so layout, paint and composite all run 18 times. Animate box-shadow, and the boxes stay put, but every frame needs new shadow pixels, so paint runs 18 times.

Animate transform or opacity on a drawer with its own layer, and the browser only moves or fades the stored picture. The grid shows which stages each property repeats.

There is a second win. CSS transitions and animations of transform and opacity can run on the compositor, a separate thread that does not wait for your JavaScript. If a re-render blocks the main thread for 100 ms, a width animation loses about 6 frames, while a transform animation keeps moving.

The fix

Give an overlay drawer its final width once, then slide it in from off screen with a transform.

/* Before: the width changes, so layout runs every frame */
.drawer { position: fixed; right: 0; width: 0; overflow: hidden;
          transition: width 300ms; }
.drawer.open { width: 420px; }
/* After: fixed width, only the picture moves */
.drawer { position: fixed; right: 0; width: 420px;
          transform: translateX(100%); transition: transform 300ms; }
.drawer.open { transform: translateX(0); }

Watch out

  • A transform moves the picture but not the box's layout slot, so neighbours do not move aside. If they must, use FLIP (next section).
  • Styles set from requestAnimationFrame always run on the main thread, even for transform. Prefer a CSS transition or element.animate() for simple motion.

Evidence

The Motion guide notes that a re-render can easily take over 100 ms. That is about 6 lost frames for any animation that needs the main thread.

How do you animate a reorder without animating layout?

The idea Apply the final layout at once, use a transform to draw each row at its old spot, then slide that offset to zero.

Walk through it

A list shows notes A, B and C, and each row is 32 px tall. The user pins C, so it jumps to the top. Animating top or margins would redo layout on every frame. FLIP avoids that in four steps: First, Last, Invert, Play.

First: read C's position before the change, which is 64 px from the top. Last: move C to the top in the DOM and read again, which gives 0. Invert: subtract first minus last, so 64 minus 0 is plus 64 px. Setting translateY(64px) draws C exactly where it was.

Rows A and B each moved down one slot, so their offsets are 0 minus 32, which is minus 32 px. Play: animate every offset to zero over 300 ms. In the diagram, small dashed boxes are layout slots and big boxes are what you see. Only step 4 runs on every frame.

The fix

Read every row's position, reorder once, read again, and animate the signed difference to zero. The reads happen once, and the 300 ms of motion is pure transform.

// Before: the pinned row jumps to the top
list.prepend(pinned);

// After: FLIP every row
const rows = [...list.children];
const first = rows.map((r) => r.getBoundingClientRect().top); // First
list.prepend(pinned);                                           // Last
rows.forEach((r, i) => {
  const dy = first[i] - r.getBoundingClientRect().top;          // Invert
  if (dy) r.animate([{ transform: `translateY(${dy}px)` },
                     { transform: 'none' }], { duration: 300 }); // Play
});

Watch out

  • Read all first positions before the change and all last positions after it. Mixing a read and a write per row forces layout again and again (lesson 17).
  • Scaling with FLIP can stretch text, and starting a new FLIP while one is still running needs care.

Evidence

The FLIP article fits the one-time measuring into the roughly 100 ms after a click, a delay users do not notice.

Why is animating a shadow slow?

The idea Every new shadow size has to be painted from scratch, so paint one fixed shadow and fade it in with opacity.

Walk through it

A card lifts on hover: its shadow grows from nothing to a soft 24 px edge over 300 ms. At 60 Hz that is 18 frames (lesson 21). Each frame has a different shadow, so the browser must paint it again. Painting here means working out the soft edge and turning it into pixels, which is called rasterising.

Now paint the full shadow once, on a separate box behind the card, and change only that box's opacity. Opacity is applied when layers are stacked, so the stored shadow pixels are reused. In the diagram, each red cell is a paint and each green cell is a cheap blend. The top row paints 18 times; the bottom row paints once.

The fix

Put the shadow on ::after, a box that CSS generates for you. Keep the shadow itself fixed and transition only its opacity.

/* Before: a new shadow is painted on every frame */
.card { transition: box-shadow 300ms; }
.card:hover { box-shadow: 0 8px 24px #0004; }
/* After: one fixed shadow, only its opacity changes */
.card { position: relative; }
.card::after { content: ""; position: absolute; inset: 0;
  border-radius: inherit; pointer-events: none;
  box-shadow: 0 8px 24px #0004; opacity: 0; transition: opacity 300ms; }
.card:hover::after { opacity: 1; }

Watch out

  • The ::after box may get its own layer while it fades, which costs memory (section 3).
  • The Motion guide lists filter: drop-shadow() as a swap for animating box-shadow. Check either choice with Paint flashing.

Evidence

None of the sources measured this exact case, so treat it as a rule of thumb. The Motion guide ranks box-shadow as paint-only: cheaper than layout, dearer than transform and opacity.

Why is a blur so expensive, and how do you fade one in?

The idea A blur mixes every pixel with its neighbours, so blur a few fixed copies once and cross-fade between them with opacity.

Walk through it

To blur, each output pixel becomes an average of the pixels around it. The blur radius says how far around it looks. With a radius of 4 px, a simple blur reads a 9 by 9 square, which is 81 pixels, for every pixel. At 8 px it reads 17 by 17, which is 289. Real blurs take shortcuts, but the cost still grows with the radius and the area.

Now animate a backdrop's blur from 0 to 8 px over 300 ms. Every frame has a new radius, so every pixel of the backdrop is blurred again, 18 times. The cheaper way is a cross-fade, which blends one picture out while another comes in. Keep a sharp copy, a 2 px copy and an 8 px copy, each blurred once, and change only opacity. In the diagram, each pair of lines crosses at a 50/50 mix, so the blur seems to grow smoothly.

The fix

Stack the copies, promote their shared wrapper to a layer, and transition opacity in turn. Each copy on top hides the one below as it fades in, which gives the crossing lines above.

/* Before: the blur radius changes on every frame */
.backdrop { transition: filter 300ms; }
.dim .backdrop { filter: blur(8px); }
/* After: blurred once, only opacity changes */
.stack { will-change: transform; }  /* promote the wrapper */
.copy-2 { filter: blur(2px); } .copy-8 { filter: blur(8px); }
.copy-2, .copy-8 { opacity: 0; transition: opacity 150ms; }
.dim .copy-2 { opacity: 1; }
.dim .copy-8 { opacity: 1; transition-delay: 150ms; }

Watch out

  • This only works for content that does not change, because each copy is blurred once. For live content, a plain translucent tint may be enough.
  • Every copy is another full-size layer. Start with one blurred copy and add levels only if the fade looks wrong.

Evidence

In the blur article, four cross-faded copies held a steady 60 frames per second, even on a low-end phone.

What do layers and many small animations cost?

The idea A layer costs about 4 bytes of memory per device pixel, and every running animation costs CPU on every frame, so keep both counts small.

Walk through it

A layer is a piece of the page stored as its own picture, so it can be moved or faded without painting again. That picture needs memory, often on the graphics card (GPU). A rough estimate is width times height in device pixels, times 4 bytes, one each for red, green, blue and transparency.

Device pixels are the screen's real dots. On a high-density screen with 2 device pixels per CSS pixel, a 300 by 200 card becomes 600 by 400. That is 240,000 pixels, or about 1 MB. A full-screen 1440 by 900 backdrop becomes 2880 by 1800, about 21 MB. The three blur copies from section 2 are about 62 MB.

Animation count is a separate cost, paid in CPU instead of memory. Even a cheap opacity animation needs a new value on every frame. One spinner with 25 pulsing dots runs 25 animations, so 20 spinners run 500, as the grid shows.

The fix

Promote an element to a layer only while it moves, and replace many tiny animations with one pre-made animated image per spinner.

/* Before: a permanent layer on every card */
.card { will-change: transform; }
/* After: a layer only while it is dragged */
.card.dragging { will-change: transform; }

/* Before: 25 animations per spinner */
.spinner .dot { animation: pulse 1.2s infinite; }
/* After: one animated image, tinted with the text colour */
.spinner { mask-image: url(spinner.apng); background: currentColor; }

Watch out

  • Rotating one wrapper is cheaper still, but it changes the look: the dots spin together instead of pulsing in turn.
  • An animated image still has to be decoded as it plays, and it needs a build step. Respect reduced-motion settings in both versions.

Evidence

With 20 spinners on screen, switching to one animated image each cut total CPU use by about three quarters.

Where does the time after a click go?

A click can spend more time waiting to run than running its own code.

Walk through it

You click Sort while the page builds previews for another tab. The main thread runs page JavaScript and prepares screen updates. It finishes its current task, one unit of work, before it can run the code that handles your click.

Read the diagram from the click mark. Input delay covers the rest of the preview work. Processing time covers the click code, which sorts and updates the list. Presentation delay lasts until the next paint, when the browser draws the screen.

In this example the click waits 280 ms, then takes 60 ms to run and 20 ms to reach the next paint. With hundreds of notes, the preview build can dominate the wait.

Interaction to Next Paint (INP) describes responsiveness over a page visit. It uses one of the slowest clicks, taps or key interactions. On a visit with only a few interactions, it uses the slowest one.

The fix

Record the click in your browser’s Performance panel and see which phase is longest. Build the previews when their tab opens, so Sort can run sooner during startup.

// Before
const previews = buildPreviews(notes);
previewTab.onclick = () => showPreviews(previews);
sortButton.onclick = sortNotes;

// After
previewTab.onclick = () => showPreviews(buildPreviews(notes));
sortButton.onclick = sortNotes;

Watch out

  • When processing or presentation takes most of the time, look at the click code and the browser’s drawing work before changing unrelated tasks.

How can a long job give other clicks a turn?

Split work across tasks so input and paint can run in the gaps.

Walk through it

Someone opens Previews. If the browser builds all four previews in one task, a click during the first must wait for the rest.

Yielding ends the current task and lets the remaining work continue in another task. The diagram shows one possible schedule. Sort arrives during the first preview and the browser handles it and paints before starting the next preview.

With hundreds of previews, a pause between small groups keeps any one group from taking over for the whole build. Awaiting an already resolved promise queues a microtask, a short callback the browser runs before it can handle input or paint. Repeating that await keeps the work together from the browser’s point of view.

The fix

In an async handler, use scheduler.yield() when available or wait for a timer task. That gives the browser a turn before your function resumes.

// Before
for (const note of notes) buildPreview(note);

// After, inside an async handler
for (const note of notes) {
  buildPreview(note);
  await (globalThis.scheduler?.yield?.()
    ?? new Promise(resolve => setTimeout(resolve, 0)));
}

Watch out

  • Choose group sizes by measuring time on a slower device. Too many pauses stretch the total time, and one expensive item can still block input.
  • Check whether the user closed the tab or changed the notes while the job was paused before adding more previews.

Evidence

On one machine in the Node demo, replacing resolved promises with timer yields cut the delay before the test timer ran by about 280 ms.

What can wait until the screen responds?

Make the visible change first and give the browser a chance to draw it before running optional work.

Walk through it

Open an Edit dialog with a title field. Moving the typing cursor into that field can make the browser calculate element sizes and positions, which is called layout. Changing a style on the whole page can also make the browser check styles for many elements.

In the diagram, the first version opens the dialog and does both jobs before the browser can paint. The second version opens it and lets the browser paint before later work in this example. On a page with hundreds of elements, even one broad style change can slow that first frame.

The fix

Open the dialog and put keyboard focus on its Close button. Then ask for a requestAnimationFrame callback, which runs before a paint. Scheduling a timer from that callback gives the browser a chance to paint before the optional updates.

// Before, immediately after opening
titleField.focus();
document.body.classList.add('l23-editor-open');

// After, with Close focused on open
requestAnimationFrame(() => setTimeout(() => {
  if (!dialog.open) return;
  document.body.classList.add('l23-editor-open');
  if (document.activeElement === closeButton) titleField.focus();
}, 0));

When closing a large panel, hide it first. Then remove its old elements in later tasks.

Watch out

  • Check in a recording when the browser actually draws.
  • Keep background clicks blocked while the dialog is open, even before the optional style runs. If users need to type immediately, focus the field when the dialog opens.

Which replies does the first screen have to wait for?

Start with the chain of replies the browser needs before it can show the first screen.

Walk through it

A shared link opens a note. A redirect sends the browser to a new address. The browser gets the HTML there and finds the script to download.

The script calls a data server at a different origin, which means its scheme, host or port differs. Because the request sends an Authorization header, the browser first asks for permission with an OPTIONS request called a CORS preflight. Once it has permission, it requests the note and can show it.

Each request and reply is a round trip. There are five in this example, and each waits for the last one. This chain is the critical path to the note appearing. More data can make each wait longer, especially over a slow connection.

The fix

First link straight to the note address. If you control both paths on the same origin, you can also serve the note at the old address. Then serve the data endpoint on the page’s origin, which removes the browser’s preflight for this request.

// Before: the server redirects this link
const noteLink = '/open-note/42';
const dataURL = 'https://api.example.com/notes/42';

// After: direct link and same-origin data endpoint
const noteLink = '/notes/42';
const dataURL = '/api/notes/42';

Watch out

  • Keep redirects that must change the scheme or host. Keep serving old shared links.
  • A server that forwards requests to the data service may add its own wait. Keep authentication in place and measure the full chain again.

Evidence

In one test on a mobile network, removing a redirect chain brought the first meaningful byte about 300 ms sooner.

Which scripts need to run while the page starts?

Let the browser read the first screen’s HTML and save optional scripts for when people use them.

Walk through it

A note page has a script above its title. The browser’s HTML reader, called the parser, pauses at the tag. It reads the title after the script downloads and runs.

With defer, the browser downloads that script while it keeps reading the HTML. In the diagram the script runs after reading ends. Paint, when the browser draws the screen, can still come afterward.

A script that handles one button may cost little. If it also loads export tools and every editor feature, the browser spends more time downloading and preparing code before the page is ready.

The fix

Use defer when an external script can run after the HTML is read. Keep the note in the initial HTML when the server already has it. Client code can read that data with JSON.parse from a type="application/json" script tag.

For an optional Export button, load its code with import() on demand. This is code splitting, which puts the optional feature in a separate file. The first screen then skips its download and setup.

<!-- Before: the browser pauses reading for the script -->
<script src="/note-tools.js"></script>

<!-- After: the defer script sets up the existing button -->
<script src="/note-tools.js" defer></script>
// In note-tools.js, load export code when needed
exportButton.onclick = async () => {
  const { openExport } = await import('./export.js');
  openExport();
};

Watch out

  • If a deferred script creates the first screen, that screen still waits for the script to run.
  • When putting JSON inside HTML, escape literal < as \u003c in the serialized data. This keeps a value from closing the script tag.

Evidence

In an audit on a mid-range phone, running startup JavaScript took about five seconds.

When does the main content appear, and what makes it jump?

Start loading the main image early and tell the browser how much room to give it.

Walk through it

Largest Contentful Paint (LCP) measures how long it took from navigation for the largest eligible piece of visible content to appear. An image or a block of text can be that piece. In this example the visitor waits without interacting, so the photo supplies the final time.

Now look at the paragraph in the next diagram. If the browser first gives the photo no room, the photo pushes the paragraph down when it arrives. Cumulative Layout Shift (CLS) scores the burst of unexpected movement with the most impact. Content that moves farther or takes up more of the screen can contribute a larger score.

The fix

Put the image in the initial HTML so the browser finds it while reading the page. Give it its actual width and height so the browser can reserve space using the right shape.

<!-- Before: a script adds this after the app starts, with no size -->
<img src="photo.jpg" alt="A fern">

<!-- After: present in the initial HTML -->
<img src="photo.jpg" alt="A fern" width="600" height="300">
<style>img { max-width: 100%; height: auto; }</style>

Watch out

  • Keep the likely LCP image out of lazy loading, which delays the request until the browser decides the image is needed.
  • A fast photo can still move the text if its space was missing. Check both when the main content appears and where the text sits across successive frames.

Why does a tiny command take so long to start?

The idea Load each module when the command reaches the code that needs it.

Walk through it

The fix

// Before: both writers load on every run.

// After: load only the chosen writer.
if (format === 'pdf') require('./pdf').write(notes);
else require('./text').write(notes);

The same idea works in a VS Code extension, an add-on that runs inside the editor. An activation trigger such as onLanguage:typescript tells the editor to start the extension when a TypeScript file opens.

How can you make a type cheaper to check?

Walk through it

NoteProps needs the fields from NoteMeta and Timestamps, plus a title. The intersection written with & asks for all three parts at once. To check a value against it, TypeScript can have to check the parts separately.

An interface names the fields an object must provide. With extends, it brings in the fields of other object types. In the comparison diagram, the first call still checks the fields, and the second can reuse the saved result for the same pair of types.

A union written with | accepts any of its member types. A function that reads just id may accept three kinds of notes through a union. To simplify a union, the checker may compare members in pairs to see which already fit other members.

Three members give three possible pairs. With 50 members, there are 1,225 possible pairs because each member has 49 partners and each pair would otherwise count twice.

The fix

Give NoteProps one interface so the checker can reuse a comparison. Give noteId a shared type if any object with a string ID is valid input.

// Before
type NoteProps = NoteMeta & Timestamps & { title: string };
function noteId(note: DraftNote | PublishedNote | ArchivedNote) {
  return note.id;
}

// After
interface NoteProps extends NoteMeta, Timestamps { title: string }
interface HasId { id: string }
function noteId(note: HasId) { return note.id; }

Watch out

  • Check accepted and rejected calls after the change. An interface can report a conflict where two base types define the same field differently.
  • Keep the union if callers must pass only those note kinds. Test inline object literals because a shared shape can reject fields it omits.

Why do two objects with the same fields look different to the engine?

The idea Objects built with the same fields in the same order share one hidden layout, so the engine reads a field by position instead of searching for it by name.

Walk through it

This lesson uses V8, the engine inside Chrome and Node.js. An object looks like a bag of names and values, but searching a bag by name on every read would be slow. So V8 gives each object a hidden class, a shared description of its layout. V8 calls it a map, and other engines call it a shape.

A map says which slot holds each field, for example "x is in slot 0, y is in slot 1". The object itself stores only the values, plus a pointer to its map. When V8 knows the map, reading p.y becomes "go to slot 1", with no search at all.

Maps grow one field at a time. Start from an empty object and add x, and you move to a map that has x. Add y and you move to a map with x, then y. Each step is called a transition. V8 remembers it, so the next object built the same way lands on the same map.

Take three points. Points a and b are built as { x, y }, and c is built as { y, x }. In the diagram, a and b take the top path and share one map. Object c adds y first, so it takes the bottom path and ends on a different map, even though it has the same two fields.

Now scale it up. If 10,000 rows are built by one function, they share one map. If they are built in three places with three field orders, there are three maps. Adding a field later, as in if (vip) row.discount = 0.1, splits them again.

The delete operator is worse. Removing a field usually makes V8 give up on maps for that object and switch it to dictionary mode. The object gets its own private table of names and values, so every read becomes a search by name. In the second diagram, only the right object still uses the shared map.

The fix

Build each kind of object in one small factory that writes every field in the same order. Store null or undefined for a field with no value, and set a field to undefined instead of deleting it.

These three are not the same to your code. A missing field is skipped by Object.keys and the in operator. A field set to undefined still shows in Object.keys, but JSON.stringify leaves it out. A field set to null shows up everywhere, JSON included.

// Before: the shape depends on which branch ran, and delete leaves the map
const row = { id: item.id, draft: true };
if (item.sale) row.discount = item.sale.pct;
delete row.draft;

// After: one factory, every field, same order
const makeRow = (item) => ({ id: item.id, draft: true, discount: item.sale?.pct ?? 0 });
const row = makeRow(item);
row.draft = undefined; // the slot stays, so the map stays

Watch out

  • Copying without the field (const { draft, ...rest } = row) also avoids delete. But it allocates a new object, and any code holding the old object still sees draft.
  • A map also records what kind of value each field has held. Start number fields as numbers, not as null. A field that will hold decimals should start as a decimal.

Evidence

In TanStack Start's server rendering, replacing one delete with an assignment to undefined cut that function's CPU time by more than half.

Why can a fifth kind of object make a loop several times slower?

The idea Each property read keeps a tiny cache of the maps it has seen, and once that cache overflows, every read falls back to a much slower general lookup.

Walk through it

Take total += item.price inside a loop. V8 attaches a tiny memory to that one read, called an inline cache. It stores pairs of map and slot, such as "if the item has map A, price is in slot 1".

Say items come from two places. Items built as { name, price } have map A, with price in slot 1. Items built as { price, name } have map B, with price in slot 0. In the diagram, an item with map B arrives. The cache checks map A first and fails, then checks map B and matches, so it loads slot 0.

A read site that has seen only one map is monomorphic, meaning one form: one check, then a direct load. With two to four maps it is polymorphic, meaning several forms, and it checks them in turn. That is a little slower.

In the V8 version measured here, the list holds four maps. A fifth makes the site megamorphic, meaning many forms. V8 stops keeping a list. It looks the property up in one big table shared by the whole program, which is far more work. The limit of four is version-specific and can change.

The demo sums .x over 1,000 objects of a chosen number of shapes, 20,000 times. That is 20 million reads through one read site. In the chart, one to four shapes stay close. The fifth makes the same loop about three and a half times slower than four.

The fix

Turn objects into one shape at the edge, before they reach the hot loop. A factory that always writes the same fields in the same order gives every item one map, so the read site stays monomorphic.

// Before: items from three sources reach the hot loop in their own layouts
const all = [...cartItems, ...savedItems, ...importedItems];

// After: one factory, so every item shares one map
const toItem = (s) => ({ id: s.id, price: s.price, qty: s.qty ?? 1 });
const all = [...cartItems, ...savedItems, ...importedItems].map(toItem);
let total = 0;
for (const item of all) total += item.price * item.qty; // one map seen here

Watch out

  • Two to four shapes are usually fine. Only fight for one shape when a profile shows the loop is hot.
  • The copy costs time and memory too. Time the whole job, copy included, before and after.

Evidence

A TypeScript prototype that gave all syntax tree nodes one layout cut total compile time by about 16 percent, for about 3 percent more memory.

  • Create each kind of object in one place, with every field present, in the same order. Do not delete fields in hot code.
  • A read site that sees more maps than its cache holds (four in current V8) goes megamorphic and can run several times slower. Normalise objects before the hot loop.

Why does V8 throw its fast code away?

The idea Optimised code is built on a guess about the objects it will see, and when an object breaks the guess, V8 drops the fast code and goes back to the slow interpreter.

Walk through it

V8 first runs a function in an interpreter, which is slow but records what it sees, such as "every argument had map A". This record is called type feedback. Once the function is hot, an optimising compiler turns it into machine code that assumes the feedback stays true.

Take getX(p), which returns p.x. After many calls with { x } objects, the fast version is short: check that the map is A, then load slot 0. That check is called a guard, because it protects the guess.

Now a { y, x } object arrives, with map B. The guard fails, so the fast code cannot continue safely. V8 jumps back to the interpreter in the middle of the call. This is a deoptimisation, or deopt, also called a bailout.

In the diagram, time runs top to bottom. The green box is the fast code. At the red arrow the guard fails, and the function drops back to the slow lane. It records map B as well, and V8 may compile it again later with two checks.

One deopt costs little. The problem is a hot function that keeps meeting new shapes, so it bails out, recompiles and bails out again.

The fix

Give hot functions stable inputs by building their objects in one factory, as in lesson 27. Then confirm with --trace-deopt, which prints a line each time V8 bails out, with the function name and the reason.

// Before: two creation sites, two key orders
const a = { x: 1, y: 2 };
const b = { y: 3, x: 4 };            // map B reaches getX: bailout

// After: one factory, one map
const point = (x, y) => ({ x, y });
const a = point(1, 2), b = point(4, 3);
// Check: node --trace-deopt app.js 2>&1 | grep bailout

Watch out

  • A few deopts during warm-up are normal. Worry only when the same hot function bails out again and again.
  • Optimisation rules change between V8 versions, so check on the Node version you ship.

In one open-source query engine, giving every change event one fixed layout made hot query paths up to 18 percent faster.

What does your build do to a for...of loop?

The idea If your build target is older than the runtime you ship to, the compiler rewrites modern syntax into helper code that runs on every loop step.

Walk through it

A build tool such as TypeScript or Babel can downtranspile your code. That means rewriting new syntax into older syntax, so it runs on old browsers. The oldest version it must support is the build target, such as ES5 (from 2009) or ES2020.

ES5 has no for...of, so the loop must be rebuilt from older parts. In the first diagram, the top box is the three lines you wrote. The bottom box is a simplified version of what a Babel-style ES5 build ships.

Follow one step. The helper it.n() is called, it creates a small result object holding value and done, the loop checks done, and then it reads value. A plain index loop only compares i with the length and reads items[i]. The second diagram puts the two side by side.

Now scale it up. A loop over 10,000 items makes 10,000 helper calls and up to 10,000 throwaway objects. The engine can sometimes optimise this away, but profiles of real libraries show the cost often stays.

The fix

Set the build target to the oldest runtime you really support. Current Node versions and current browsers run ES2020 syntax natively, so a modern target ships for...of, classes and let as written.

// tsconfig.json before: every for...of goes through a helper
{ "compilerOptions": { "target": "ES5", "downlevelIteration": true } }

// after: the loop ships as written
{ "compilerOptions": { "target": "ES2020" } }

Watch out

  • Libraries ship their own build. Read the file your app loads from node_modules, not the source on GitHub.
  • If you must support an old target, write the hot loop as a plain index loop, so there is nothing to rewrite.

Evidence

In esquery, which ESLint uses to match code patterns, avoiding the downtranspiled for...of saved about 2 seconds of a lint run.

Is the newest syntax always the fastest?

The idea No: sometimes the older form runs faster, and the winner changes between engines and versions, so measure the built file on the runtime you ship.

Walk through it

Native for...of still uses the iterator protocol underneath. graphql-js moved its build target from ES5 to ES2020, and its hot loops over Map entries now ran through that protocol. Building a schema then ran about 22 percent fewer times per second, although later reruns gave mixed results. The whole new build caused that, not only the loops.

let and const come with a check that a variable is not read before its declaration has run. That window is called the temporal dead zone (TDZ). In TypeScript's own huge compiler file, V8 could not always skip those checks, so the team changed the hottest variables to var by hand.

The chart shows an experiment that turned every let and const into var. It cut parse time in one benchmark from 3.93 to 3.52 seconds on Node 18. On Bun, which uses a different engine, there was no difference. Preact's signals library made a similar call, turning its classes into plain functions with prototype methods because they were faster in its benchmark.

So none of these is a rule. Each result is one engine, one version and one hot path.

The fix

Do not rewrite a whole codebase in old syntax. Profile the built output, find the one hot loop, and write it in a plain form that every target handles the same way.

// Before: a hot loop that goes through the iterator protocol
for (const [key, value] of map.entries()) use(key, value);

// After (the graphql-js approach): an index loop over a plain array
const entries = Array.from(map.entries());
for (let i = 0; i < entries.length; i++) {
  const { 0: key, 1: value } = entries[i];
  use(key, value);
}

Watch out

  • var ignores blocks, so it can leak out of loops and if bodies. Keep tricks like this for compilers and parsers that run billions of steps.
  • Re-measure after each Node or browser upgrade, because these gaps open and close between versions.

Evidence

In an experiment, switching TypeScript's compiler to var cut parse time by about 10 percent on Node 18.
